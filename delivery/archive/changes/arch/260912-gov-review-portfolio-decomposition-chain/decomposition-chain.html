第 ① 步 · 立项

PROPOSAL（主线程起草 + human grilling）

主线程按 WORKSTREAM-PROPOSAL.template 起草（输入常为人机讨论产物）→ human 裁 OQ → architect 分流 review（/triage-change，已有）→ 冻结
角色：三问 + 裁定 · 冻结后不动frontmatter 标 workType（new-capability / remediation / refactor，可混合、按业务目的逐条标）。
.planning/<ws>/PROPOSAL.md = 通用三问 + 分型：
  • ① 要达成什么 硬项——业务目的清单，每条可观察判据；来源随分型：整改引缺陷证据 / 新建引 spec story（不改语义只加判据）
  • ② 现在在哪——新建型：现状盘点 + 能力差距（「还没建」≠「坏了」）；整改型：问题 + 证据锚 + 根因（「问题与根因」仅此形态合法）；重构型：结构痛点
  • ③ 怎么走——方案空间 + OQ 裁定，每条裁定标注 spec 关系 硬项：within-spec（spec 已定，只选路径，引条款号）/ 需修订（要改 spec 语义 → 先过 spec 修订流程，spec 改完前受影响包不得 launch）/ spec 未载 → 留根登记
  • 非目标 + 契约 / spec 触面申报
  • §4 拆包预判降级→ 只作意图提示，不再当拆包权威
两源权威序：spec = 行为语义权威，PROPOSAL = 路径选择记录——裁定改 spec 钉死的语义必过 spec 修订，不得自冻成第二事实源。（MVP 教训：新建型的目标句写成「把 story 拆成包」这个动作本身，业务效果一处未落纸——① 的硬项由此来；260911 全整改所以「问题与根因」成立，但形态不通用）
→
第 ② 步 · 拆包

portfolio-planner（RTE）拆包

输入 = 冻结 PROPOSAL → intake 核模板符合性（缺业务目的清单 / workType / spec 标注 → fail-closed 打回，不猜不代写）+ 图索引只读探查
角色：把裁决变成列车计划一次拆包产出「四件套」，缺一不齐不得交 launch。
拆包规则组（v0.7 提案 · 待 human 确认）：
  • 元规则 · demo 点——每包必提名一个「看得见、摸得着」的东西，三形态：行为（业务包：孩子/家长能看到听到按到）/ 示踪弹（基建包：载着一件最小真货跑通一趟——「建好了」不算，「能用」才算）/ 回归 + 结构齿（重构包：老行为全绿 + 新结构性质被一条齿钉住）
  • 切缝——默认沿行为缝切（行为是纵向的，文件/系统/Pod 是横向的，掉缝都发生在横切处）；横切（技术层 / 系统段）合法但须付费：① 带示踪弹 ② 服务的业务包在 dependsOn 点名它；跨缝行为显式 owner
  • 粒度上限——一个包 = 一个 demo 点；多个结果共享热文件时按序三选：抽缝包先行（先冻接口）→ 串行 mergeOrder → 一个包 + 阶段级 demo 点
  • 粒度下限——包价值 > Pod 固定开销（worktree / 图索引 / integrator / supervisor / merge）；说不清「我的 demo 点 + 我挡掉的阻塞」就合回去
拆包四件套：
  • roadmap.md 新增·活文档——业务目的清单分解到包、列车图（机械渲染）、每包「完成后人能看到什么」+ demo 点（三形态）、达成状态
  • taskpackage.json × N 已有——机器骨架（dependsOn / mergeOrder / acceptance）+ packageKind + demo 点声明
  • plan.md × N 收紧——每包必备初步设计，装配型豁免取消（MVP 19/19 缺位的根治）
  • decision-coverage.json 已有——决策 → 包 → 验收，机器对账
门 1 · 拆包 review（新增，GREEN 才 commit-before-launch）
  1. 切片逻辑：按规则组判——行为缝 / 横切付费 / 粒度上下限，图上见
  2. 依赖序 + WIP 合理性
  3. decision-coverage 完备（含跨包行为 owner）
  4. 每包意图与 PROPOSAL 冻结裁定一致 + demo 点三形态在位
  5. demo 证据形态可行（真机轮配额仅核心包）
architect 轻量 review（OQ1 可裁改对抗档）→ GREEN 后 human 过目切法——方向 + 切法一次前端对齐，切法自此有票
→
第 ③ 步 · Pod 内执行

planner（单 Pod 开发循环）

拿到并消费：plan.md（只读，包级设计）+ roadmap 本包效果段（意图锚）+ taskpackage.json 骨架 + 冻结 PROPOSAL
  • 派 acceptance-author——brief 必须携带 roadmap 本包效果段（「回答期间图表前台可见」这类可观察不变式的稳定落点）
  • 锚 2 · 验收方向核（新增）planner（agent）在 acceptance 冻结后、builder 动工前，对照 roadmap 效果段核验收方向对不上 / 存疑 → 升 architect 复核；human 只在升级链终点出场
  • builder → verifier ↔ fixer（内循环，不动）
  • integrator 收口
  • 锚 3 · demo 对账（新增）收口必含 demo 证据（形态拆包时已定）+ 与效果段的一致性结论对不上 → 走既有 escalation 通道就地升裁，禁攒到集成夜
  • supervisor 合并门 → merge-driver 合并（已有，不动）
闭环（列车视角）——匹配判断在锚 3（合并前）完成；绿路径上 RTE 沉默，列车靠 board + 脚本自己跑：
包 merge→ 状态机械渲染（render-roadmap：merge = achieved / deviation 标注）→ reconcile 机械算下一包 ready（依赖满足 + WIP 未满 + mergeOrder 最靠前）→ human 照常点火下一包（现行流程不变，RTE 不出场）→ 全列 achieved → workstream 收口轮
portfolio-planner 仅在调度异常时由 human 唤起重裁：锚 3 deviation 影响后续包 / 依赖关系与实际不符 / WIP·mergeOrder 需重排。
