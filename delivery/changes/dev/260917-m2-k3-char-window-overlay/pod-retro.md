## 卡点与体感

1. **拆包产物的「元数据 vs 磁盘现实」落差，连续第三棒命中，而且这次是两处**。`origin.type` 枚举值不在闸的值域闭集内（裸跑形态闸直接报红），`sourceRefs` 又漏了四处真实改动面——最要命的是漏掉了 `kidpal_render_node.h/.cc`：那里面有两处被上一个包明确标注「保留不动、由 M2-K3 改窗时统一收，禁静默删除」的写侧死态 API，本包就是那个承接包。这四处没有一处会被机械闸抓到，全靠 intake 期逐一打开代码面核。体感依旧是那句：**拆包产物到手时已经是一份有保质期的快照，intake 期的读代码面不是可省的成本项，是唯一的提前发现手段。**

2. **上一包 retro 写的动作清单，这一包真的当清单用了，回报立刻可见**。「派发书里的必改钉点一律写成『已知的、非穷尽的』并要求对面做完备性反查」——这次我照做了，验收作者也照做了，结果是**它主动反查出我清单里没有的一处必改点**（上一包立的两条「保留不动」守卫齿，本包收拢后必假红），还顺手独立发现了第二处问题（见第 4 条）。上一包是靠运气，这一包是靠条文。体感：**retro 写成动作清单真的会复利**，这条我连续两包验证了。

3. **最让我意外、也最值得记住的一件事：实现者拒绝了「脑补实现」并如实上报，而这恰恰是正确动作**。5 分钟驻留的纯逻辑模块做完了，但设备侧驱动（谁来喂时间、谁来归零、到点谁去关窗）全仓零消费者——冻结验收只钉了纯逻辑模块，没钉驱动。实现者的判断是：无本地板、无法证实「在 LVGL 定时器回调里关窗」的递归与时序安全，所以不自己发明落点、把缺口交回来。**这个处理比它自己补一个驱动要好一百倍**——它要是闷头补，我会拿到一个「齿全绿但真机上没人知道对不对」的包，而且没人会知道哪里不对。**另一头是验收面的责任**：冻结 seam 只钉了半条承重链，是我派发时没问出「这条验收的落地面钉到驱动层了吗」。判归属→路由补钉→补实现这条链这次跑通了，但代价说明**验收面欠覆盖这件事，机械闸一条都拦不住**。

4. **验收冻结的齿，被实现者用变异反过来证伪了——这是我完全没预料到的**。实现者做自证变异时发现：我冻的一条「某行补上屏」的齿，用「切区内出现某符号计数 ≥1」实现，**只要在注释里写一遍那个符号就算过**；它删掉自己写的说明注释前，那条变异根本不红。也就是说这条齿在「注释即满足」的形态下是**假绿**的。我把它路由回验收面收紧（引入注释剥离器后重测，注释再也满足不了），并且**同类齿一并扫了一遍**。体感：**验收作者冻齿、实现者用变异反向检验齿强度，这个回路是真的能咬合的**——前提是实现者被要求做变异自证，且敢把「我测不红」当成结论上报而不是掩盖。这一条我认为是本包最有价值的过程收获。

5. **收口后我自己拦下了一处「本包自己引入的假陈述」，代价是让终审事实重跑一遍**。`firmware/main/CMakeLists.txt` 里那句「设备侧调用点待接」是第一轮实现者写的（当时确实未接），第二轮驱动接上后没同步，已经是错的。收口角色把它归为「建议后续 micro-fix」放进 review-packet——这是个合理的分流，但我把它推翻了：**本包自己的验收条目就是清理「头注虚标」这类假注释**（进度珠那处），同包再往主干送一条新的假注释，是自相矛盾；本仓也有「文档写了真机不存在」这条已登记的缺陷谱系。修完之后终审事实陈旧、必须重跑，所以这次「坚持诚实」是有实际成本的，我认这个成本。体感：**「本包引入的事实错误」和「既有遗留项」在收口分流里应该分开判——前者不该流入 micro-fix 池，因为它一进主干就会被下一个包当真**。

6. **挂钟停滞把验收作者整段打掉一次**。第一个验收作者实例在「已验证一处疑似假红、正扩大完备性反查」处整整十分钟没有任何工具调用进度，被流看门狗 terminate，磁盘上零制品。我按既有条文处理：**保留它已做的阅读面、用 SendMessage 复位续跑，而不是重派新实例**——省掉了重读一遍的整段成本，它接到复位指令后按「增量落盘、build/run 拆步、保持工具调用节奏」三条纪律一次跑完。体感：**「停滞不等于失败」这条在实操里是省钱的关键判断**；如果我按本能重派一个新实例，那十分钟的阅读面就白烧了。这条经验值得固化。

## 别扭的 acceptance / 帮倒忙的钩子

- **commit-safety 钩子的提示口径依旧误导**：`git add` 之后它弹「staged 为空——git add 可能未生效」，而它读的是 add 之前的快照。上一包 retro 已经记过一次，这一包至少又踩了三回。两次都无害（多跑一步 `git diff --cached --stat` 就能确认），但**同一条已登记两次的噪声提示，值得在下一批治理里修掉**——它消耗的是每一棒 Pod 的注意力，而不是某一棒。
- **闭环里有两处「全绿但没人真跑过」的盲区**：设备侧驱动那处前面说过；另一处是**结构齿只能靠扫源码**（那些文件不进 host 构建），所以「页→窗」的实际观感、关窗回原页的手感、键帽条是否真的还浮在上面，全部只有编译证据、没有运行证据。这些归真机轮，但**在真机轮之前，本包的「绿」的含义必须读准：是 host 行为面 + 静态结构的绿，不是整包可用性的绿**。我在 review-packet 里明确写了这一条，避免下游把「齿全绿」读成「可以交付给孩子」。
- **层数值码要动两个既有值**（为给查字窗腾出优先级位，两个更高优先级的层各上移一位）。派发前我实测过全仓消费点都是符号引用、零数值字面耦合，所以机械上安全；但仓里有一处归档件里留着写死的老数值和一条会红的断言——那件已不编入任何构建，实现者核清后判定是非活耦合、没停包也没硬改。**这个判断是对的**，但它提醒我：**「冻结」这个词在仓里指的东西不止一种**（有的冻结件每轮跑、有的只是文本冻结），派发时若不点明，实现者很容易在两种之间选错态度。

## 下次改进

- **派发前对每条 acceptance 多问一句：「这条的落地面钉到副作用层了吗？」**——本包最大的返工来源就是一条承重行为（自动关窗）的验收只钉到了纯逻辑模块、没钉驱动。写法上可以直接要求验收作者对每条 acceptance 标注「钉到哪一层（纯逻辑 / 结构 / 驱动 / 真机）」。
- **收口 findings 分级：区分「本包引入」与「既有遗留」**。本包引入的事实错误一律本包内修、不进 micro-fix 池；既有遗留照旧登记。这条可以直接写进 integrator 的派发书。
- **派发书里把「注释也是交付面」写明**：注释里的假陈述会被下一个包当真（本仓有先例谱系），且本包的验收条目里就有清理假注释的项。
- **停滞复位而不是重派**这条经验固化进我自己的默认动作：先 SendMessage 复位，除非复位后仍无进展。
- **真机轮之前的「绿」要在制品里显式限定语义**（host 行为面 + 静态结构，非整包可用性），避免下游误读——本包已在 review-packet 落地，值得升为固定条款。
