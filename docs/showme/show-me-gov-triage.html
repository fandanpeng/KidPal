dev 侧变更（改 firmware/** 行为）开工前的分流前置门。大 feature / 小 feature / bug 不分入口，先过 architect 一次比例化 review，判四档、把 reviewed plan 落到它的家。

主线程人类主会话 · 编排 + 落盘（不受 per-agent enforce-scope 限） architect只读 + 审 + 返回裁决，零写入 architect-reviewer逃生门四分类（契约预审） human人类触点（确认 / 冻结 / 起会话） planner / portfolio下一段 dev-loop 会话

零、一句话 what this gate is

它是「dev 侧」的入口闸，不是业务门。变更进来先问碰不碰单一事实源（docs/contracts/** / kernel·systems spec / .claude/agents 定义 / gate）——碰 → 跟大小无关，一律直走 /arch-change，根本不进本门；不碰（纯 firmware/server/docs）→ 进本门由 architect 判四档，human 确认后主线程把 reviewed plan 落到它的家，再报下一步该起哪个会话。
本门 convention-only（当前无机器牙齿，靠约定 + 多层人工兜底）。作者≠判官：architect 审 + 起草，FROZEN 归人类，落盘归主线程。

二、逐步：每一步谁干、怎么走到、干嘛、产出什么

  1. 主线程输入 = plan / 想法→ 你是人类主线程编排者
    输入是 plan mode 产出的实现思路、一句话（如「修复线索 SSE 重复行」）、或一份 plan 文件路径。你按 .claude/references/change-triage.md 的程序推进，每步显式说明「派给谁、为什么、期望产物」。
  2. 主线程第一刀：事实源分区→ 碰 → 升级；不碰 → 继续
    读 plan，判它碰不碰单一事实源。碰（触 docs/contracts/** / kernel·systems spec / .claude/agents 定义 / gate）→ 告知用户直走 /arch-change，本门收尾（跟大小无关，根本不进本门）。不碰（纯 firmware/server/docs）→ 进第 ② 步。这一刀把「事实源侧（Track A/B 地盘）」与「dev 侧（本门地盘）」分开。
  3. architect派 architect 比例化 review→ 四档裁决 + reviewed plan（会话内，未落盘）
    派 architect（只读 + 审），按 change-triage.md 判四档 + 出 reviewed plan。architect 只审 + 返回（同会话 return，非跨会话 prose），不写任何文件。力度按档比例化：大 feature（③拆包）= 实质单轮 review（findings 逐条 + 处置），生成 delivery/workstreams/<ws>/review.md 内容（findings + architect sign-off）；小 feature / bug（②单包）= 快审（确认判据 + 路由裁决），裁决写进 plan.md frontmatter、不单独成件。
  4. human人类触点①：确认 / 改判路由→ 档位定稿（落盘前必过）
    用 AskUserQuestion 呈现 architect 的四档裁决，人类一句话确认或改判（如 Lite→Full）。落盘前必须过这一关——Lite/Full 是安全相关判断，architect 误判需人类 backstop。
  5. 主线程主线程落盘（只搬运，不改内容）→ 三个落点之一
    按确认后的档位把 architect 的 reviewed plan + 裁决原样搬进它的家（主线程不受 per-agent enforce-scope 限）：
    · ③ 大 feature → delivery/workstreams/<ws>/PROPOSAL.md（+ review.md），frontmatter freezeState: pending-human；按 WORKSTREAM-PROPOSAL.template.md（三问 + 分型）起草，业务目的清单 / workType 数组 / spec 关系标注三项硬项缺失会在 portfolio-planner intake 被 fail-closed 打回。<ws>/ 目录由你（人类/主线程）创建 = 「设计权威落家」。
    · ② 单包 → delivery/taskpackages/<id>/plan.md，frontmatter 含 rigor / riskTier / sourceType / reviewed-by / date；建包时按 task-intake-and-slicing.md 创建 taskpackage.json + 填 origin（upstreamType / upstreamRef / upstreamFrozen / workstream）+ 注入 YYMMDD- 日期前缀 changeId + 写 planRef 指回 sibling plan.md。
    · ① 直接修 → 不落盘（地板：不改 apps 行为 / 人类明确跳过）。
  6. human人类触点②：仅大 feature 冻结→ FROZEN PROPOSAL（版本 / sha）
    人类盖 FROZEN。作者≠判官：architect 不能自冻（scope 机器兜住——architect 的 allow 不含 delivery/workstreams）。portfolio-planner 只拆 FROZEN 的 PROPOSAL。
  7. human人类触点③：报告下一步命令→ human 起自己的主线程会话
    打出人类要起的下一段会话命令：② 单包 → planner 跑 /build-feature <id>（从 plan.md 读 reviewed plan 做 intake）；③ 大 feature → portfolio-planner（指 <ws>，从 PROPOSAL.md 拆包）。planner / portfolio 必须是自己的主线程会话——子 agent 不能再派子 agent，本门拉不起那个会话；dev loop 本就该人类在场。

三、四档裁决 architect 判 → human 确认 → 三个落点

③ 大 feature · 拆包
实质单轮 review → workstreams/<ws>/PROPOSAL.md + review.md（pending-human）→ human FROZEN → portfolio-planner 拆成 N 个带依赖的 TaskPackage
② 单包 · Full
快审（确认判据 + 路由裁决）→ taskpackages/<id>/plan.md（rigor=full）→ planner 跑 /build-feature
② 单包 · Lite
快审 → taskpackages/<id>/plan.md（rigor=lite）→ planner 跑 /build-feature。Lite↔Full 误判由触点① + supervisor 兜底
① 直接修
不落盘。地板：不改 apps 行为 / 人类明确说跳过流程（须诚实记录「跳过流程」）

四、逃生门（reviewer-first）review 中发现疑似触事实源

本门无权批准

architect-reviewer 疑似触契约 / spec / agent 定义 / gate

review 中发现疑似触事实源 → 先派 architect-reviewer 四分类（不自己判、不继续落盘）。四分类结果决定去向：
CONTRACT_CHANGE_REQUIRED转契约门 + 停，升级 delivery/changes/arch/（本门无权批准）
SPEC_CONTRACT_DRIFT同上：转契约门 + 停 + 升级
NO_CONTRACT_CHANGE / ADAPTER不触契约 → 回本门按四档继续

五、关键不变量与边界 convention-only

convention-only 不变量（当前无机器牙齿）

  • 主线程只搬运 architect 的 reviewed plan，不改内容
  • 单向守卫（riskTier overrides rigor）靠人类触点① + supervisor riskTier 升级兜底
  • FROZEN 拆包门靠 portfolio-planner 自觉
  • plan.md planner 只读消费，改需留痕
  • 机器守卫记 ARQ 后续 G3（见 change-triage.md）
