## 3. 摩擦与卡点（按痛感排序）

**F1 · 改法「打错机制」——处方描述的拦截点根本不存在（本批最痛，判官标「升级 human」）**
- **现象**：`ARQ-260913-auto-mode-classifier-legit-workflow` 的处方是「派发时在 dispatch prompt 里带两句声明」。R1-F1 核三例误伤的**运行者身份**后证伪：① `char-stroke` 变异探针 = **planner 主会话直跑**（pod-events 事件原文 `"decision":"approve-mutation-probe-workflow"`、summary「human 批准 **planner 直跑**变异探针循环」）——**该拦截点无 dispatch prompt 存在**；② `story-p3` mutation 取证 = 主线程直跑——同上；③ `g-relay-fix` ECS 部署 = 子 agent，**唯此例机制够得到**。**三例里两例够不到、且恰是最疼的两例。**
- **根因**：ARQ 登记时**只记了「哪些动作被误伤」（现象），没记「误伤发生在哪条执行路径上」（机制）**；而两个执行路径（派发 / 主会话自执行）在形态上完全不同。**另**：ARQ 行自引的 char-stroke retro 模式本是「**派发/执行前**先落 human-decision 背书」——**含「执行前」臂**，处方只承接了「派发」臂。
- **证据锚**：§7 R1-F1；PROPOSAL §6 留根① 的三例运行者身份表；队列行追记。

**F2 · 「生产者可达性断链」——引先例时把「双臂结构」说成「同一层」**
- **现象**：T1 引 `pod-coordination.md:196` 的「demo 对账行」作「同层先例」。R1-F2 核实：该先例实为**双臂结构**——**口径臂**在 `pod-coordination.md`（说明「这行必须带」）、**携带臂**在 `.claude/agents/planner.md` 的派发步（告诉 planner 派发时要带上）。本批只落了口径臂 ⇒ 规则躺在参考文档里、**无人告诉干活的人去用**。
- **根因**：本仓既有条款的**承载形态常是两件套**，而引用时只看到「写在哪个文件」、没看到「谁负责携带」。**这类「写进手册 ≠ 会被执行」的差距，是本仓多起流程债的共同形态。**
- **证据锚**：§7 R1-F2；human 2026-09-19 的「**补上携带臂**」裁决（已写入留根① 与队列行）。

**F3 · 判官对「幸存 T」的两条收口也很实**
- **现象**：R1-F3 指出 T2 的指针**读者面错配**（我写的是「防真机轮派发侧想不到翻该 skill」，但该处是**收口/对账语境**、不是派发主阅读面）；R1-F4 指两处计数小失真（「两度实证」实为三次重启；「四类已实证误伤」实为 3 例 + 1 类泛化）。
- **根因**：**可达性归因**未核受众就写；**计数**来自转述而非现数。
- **证据锚**：§7 R1-F3/F4；v0.5 的据实改写。

**F4 · V6 类断言锚错区间（本批发现、已申报）**
- **现象**：FROZEN §5 V6 写「landing 后跑 `git log <FROZEN 时点 SHA>..HEAD -- .claude/scripts .claude/agents`，预期零提交」。实际跑得 **1 个 commit**——经核是**同族 P4 的合法 landing**（本族四批按序连续落地，区间内必然有别的批）。
- **根因**：该断言**隐含「区间内无其它批次落地」的前提**，而拆包族是连续落地的。**「零改动」类断言宜锚「本批 landing commit 范围」或直接用工作树状态。**
- **证据锚**：landing-summary §3-1；verdict 的独立复证。

## 4. 优化建议（按 ROI 排序）

1. **ARQ 登记「现象类」问题时，必须同时记「机制/执行路径」**（载体：**ARQ 收件箱 / `gov-arq` skill**）——F1 若在 ARQ 里就写清「三例中两例是主会话自执行」，处方不会打错。**与 P1 的建议 1 同源（ARQ 段须带验证状态），本批是其「机制面」的补充。**
2. **引用既有条款时，须同时核「口径臂 + 携带臂」**（载体：**ARQ 收件箱 / 或并入 `pod-coordination` 的写法约定**）——F2 的教训：本仓条款常成对出现，只落一半 = 规则不可达。
3. **V6 类「零改动」断言宜锚 batch-local 范围**（载体：**`docs/templates/PROPOSAL.template.md` 的验证集写法提示 / 或随下一批**）——连续落地的族里，「FROZEN 时点..HEAD」区间必含他批。
4. **可达性归因前先核受众**（载体：**ARQ 收件箱 / 或写作纪律**）——F3 的「防派发侧看不到」写之前应先问「那个文件的读者是谁」。

## 5. 一句总结

**本批最值钱的是一次「机制层证伪」：处方假设误伤发生在「派发」，而实证三例里两例是主会话直跑——那个拦截点上根本没有 dispatch prompt。** 另加一条**可迁移的结构教训**：本仓条款常是「口径臂 + 携带臂」成对的，只落一半等于没落。落地侧干净（2 路径、纯新增 +12/+2、零删除，核验官判 PASS）。
