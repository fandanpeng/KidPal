零、一句话 + 什么时候才走 Track A 触发判据

默认路由是 Track B；Track A（full-adversarial 机器）由判据触发式启用。命中任一即走：① 触 docs/contracts/**（直走契约门——契约门是独立机器，非 Track A 族）；② 跨系统结构性变更（如固件协议与服务端语义同时动）。「声明红队」= 自愿逃生门（human 或 architect 任一方随时可启，非路由义务）。存疑向严：判据适用存疑默认升 human。
作者≠判官≠核验：architect≈builder（起草候选）· scenario-author 独立冻 charter · adjudicator≈supervisor（裁）· landing-verifier≈verifier（核）。moderator 编排但不代 architect 起草、不自评通过、不替 human 拍板。

二、逐步：每一步谁干、怎么走到、干嘛、产出什么

  1. review-moderatorIntake + 分类（phase-0）→ 主 lane + contract-touching flag + review-depth
    读 plan，判主 lane（二选一）+ contract-touching flag（横切标记，非独立 lane）：
    · spec：触 docs/systems/**（canonical = requirements.md + architecture.md）的意图 / 行为 / 拓扑 / 边界 / 阶段。
    · governance：触 .claude/{agents,commands,references,rules,skills} / scope-map.json / *.settings.json / hooks/** / scripts/** / 指令根。UIUX 不是第 3 个 profile——它是携带 UIUX 轴集的 governance-lane 变更，在既有 governance profile 下审（不判审美，审美是人类品味决策）。
    · mixed（命中 >1 lane）：AskUserQuestion，默认建议拆两次跑；强耦合到必须同一 PR 时同会话先跑完 spec profile 落地再跑 governance profile。
    · 纯契约面（无 spec/gov 配套）：不在本命令处理 → 直走 architect-reviewer + 人类契约门，本命令收尾。
    分类结果必须显式展示；含糊用 AskUserQuestion，别猜。随后判 review-depth（见下卡）。
  2. review-moderator归一制品目录→ reviewDir
    spec profile → delivery/changes/arch/arch-review-<slug>/；governance profile → delivery/changes/arch/gov-review-<id>/。
  3. architect派 architect 起草候选（作者阶段）→ 候选制品（写入 ≠ 冻结）
    派 architect（起草 subagent，对偶 dev-loop builder）产候选：spec lane → spec 草案 / 候选修订写入 docs/systems（草案面，写入不等于已冻结）；governance lane → gov-review-<id>/PROPOSAL.md（不落 G1/G2/G3 canonical）。architect 只起草候选、备 review 背景 / 候选关注点 / 历史 canary 线索；不写冻结 charter、不自评可冻结、自改递归仍须 human、不自路由。
  4. architect-reviewer契约预审（仅当 contract-touching）→ 四分类 / ContractChangePacket
    派 architect-reviewer 四分类；SPEC_CONTRACT_DRIFT / CONTRACT_CHANGE_REQUIRED → 停在人类契约门，配套 spec / proposal 暂存 packet 不单独落地（原子性：与契约改动同一 PR）。
  5. review-moderator路由进 profile 跑完整对抗 loop→ findings + 裁定 + debate-log
    按 review-moderator.md Process 推进：scenario-author 冻 charter → challenger↔defender 辩论内循环（你驱动，禁止嵌套派生）→ adjudicator 裁定 + 标 outcome → 级联续问穷尽。全程维护 debate-log.md。辩论节奏 / 收敛 / deadlock / 五要点见下卡。
  6. review-moderator human落地 / 收口（profile 分叉）→ spec 落地 / gov decision-packet → human
    spec profile：低影响 CONFIRMED + 明确改法 → moderator 直接落 docs/systems；高影响 / 跨系统 / deadlock / L0 → AskUserQuestion 交 human（建议即地板）。过 pass-oracle 5 关（+ handoff 出口）方可标「可冻结」；需实现侧修复 → 产 dev-loop-handoff.json 交 /build-feature。
    governance profile：不落任何 canonical；confirmed 改法写进 decision-packet.md；治理默认高影响 → AskUserQuestion 交 human；改 agent 定义 / 自改递归 / 强制层 / 指令根必 human。过 governance pass-oracle 6 关方可标「可批准」。human 批后走定稿五步（见第四节）。
  7. adjudicator收尾：制品写盘→ 全套制品落 reviewDir 磁盘
    确认 adjudicator 已把制品写到 reviewDir 磁盘——findings.md + review-packet.md（governance 另加 decision-packet.md）+ 按域写出的 CRQ 账本条目（docs/crq/{gov,tech,requirement}/，写完跑 crq-render.mjs），debate-log.md 齐备，返回只给结构化摘要。任一制品仅以文本返回 → 退回 adjudicator 重写盘，不收口；任一 pass-oracle 关 RED → 退回重跑，不放过。

三、① review-depth：lightweight vs full architect-reviewer 判 + moderator 独立复判（双锁）

Track A 内部 G 层路由

architect-reviewer eligibility 四裁断

lightweight 仅限小 / 低风险 G2（G1 指令根 + G3 强制层新 idea 恒 full-adversarial + human，永不 lightweight）。合格面 = 仅 G2 + 机检硬排除全过 + 主观残留为空。
LIGHTWEIGHT_OK确属小 / 非契约 / 仅 G2 → moderator 独立复判（非 pass-through）→ 主线程 packet-bound landing
ESCALATE_FULL_REVIEW有架构语义 / 跨系统 / 歧义 / 落主观残留 → 走 full 对抗 loop
HUMAN_REQUIRED触 G1 / G3 / 自改递归 / 高敏 → human / full governance
CONTRACT_GATE_REQUIRED触 contracts 或 spec-contract drift → 契约门四分类 + 人类契约门
lane 分类→派 architect-reviewer 判 eligibility→LIGHTWEIGHT_OK→moderator 独立复判→主线程 packet-bound landing→记 lightweight 证据
lightweight 制品（落 reviewDir）：lightweight-intake.md / architect-reviewer-verdict.md / architect-landing-summary.md（引被批 packet-id）/ 验证输出。不得伪造 full-review 制品（review-charter.md / findings.md / review-packet.md）——full loop 没跑就没有。机检硬排除：触契约 / G1 指令根 / G3 强制层 / 改 agent tools·name·model·write scope·authority / 改 self-def·review-loop def / 增删改 gate / mixed·L0 → 一律不合格。

四、⑤ 对抗辩论内循环 + ⑥ governance 定稿五步

chal↔def 辩论内循环（⑤）

  • 每条 finding：challenger↔defender ≤ N 轮（默认 2–3），moderator 主线程驱动、禁止嵌套派生
  • 收敛：defender 承认 → CONFIRMED；defender 引具体 spec/contract 原文完整反驳 → DISMISSED（adjudicator 认证）
  • deadlock：满预算仍争 → adjudicator 打包正反最强论点 + 利害 + 各方案代价 + 推荐 → human 拍板
  • 熔断：同一 finding 反复 deadlock / 堆积超阈 → 升级人类（镜像 dev-loop 2 轮 BLOCK 熔断）
  • 五要点：falsifiable-first 排序 · 级联续问（finding 是依赖树）· 建议即地板 · elicitation 提问 · 造概念前先查重
  • 反空过守卫：scenario-author 播 regression-canaries；challenger 没能独立重派生 → RED 换更锋利 challenger，绝不改真 spec 造洞
finding outcome 六种：FIX-SPEC · FIX-DEV/FIX-IMPLEMENTATION（→ dev-loop-handoff.json）· DISMISS-WITH-GROUNDING · ACCEPT-AS-RISK · HUMAN-RULED · SPAWN-NEW-CONCERN（→ CRQ 账本延迟占位）

human 批后 governance 定稿五步（⑥）

①定稿 architect 回灌 PROPOSAL→②冻结 human 盖 FROZEN→③核验 moderator + 机械门→④landing 主线程 packet-bound→⑤landing-verifier 保真核验
  • ①定稿：architect 把所有 CONFIRMED 改法 + human 裁决回灌进 PROPOSAL.md，标 FROZEN/APPROVED + 加「Review 定稿记录」，必产 landing-manifest 围栏块。只机械回灌已批改动，不夹带新设计、不自冻（PROPOSAL 成单一权威，decision-packet 退化为 delta 记录）
  • ②冻结：human 盖 FROZEN（版本 / sha）；architect 不能自冻（作者≠判官）
  • ③核验：moderator（非作者）核对 frozen PROPOSAL ↔ decision-packet ↔ findings ↔ 裁决一致 + 跑 proposal-consolidation-check.mjs；RED 退回定稿，不放行 landing
  • ④landing：主线程 packet-bound canonical landing，architect-landing-summary.md 引 packet-id + frozen 版本
  • ⑤保真核验：landing-verifier 跑 landing-fidelity-check.mjs + 逐文件 diff，写 landing-verdict.md；绿才 human merge，RED 退回修 landing

五、两套 pass-oracle 全过才可冻结 / 可批准

spec profile · pass-oracle（5 关 + handoff 出口）

  • 1 轴覆盖—charter 每条适用轴被 challenger 走过
  • 2 场景覆盖—每个 ATAM + pre-mortem 场景走过
  • 3 finding 全结—无未结 BLOCKING/SHOULD
  • 4 spec↔contract 机械门绿—arch-spec-contract-check.mjs：无 schema 复制 + core.* 引用解析
  • 5 canaries 全中—regression-canary 被独立重派生
  • + handoff 出口—有实现侧修复时 arch-review-handoff-check.mjs 必须绿

governance profile · pass-oracle（6 关）

  • 1 治理判据覆盖—authority/owner/writer/approver 一致性、G1/G2/G3 归属、自改递归、跨面对齐、门边界、是否触契约
  • 2 finding 全结—无未结 BLOCKING/SHOULD
  • 3 高敏项已标 human—触 agent 定义 / 自改递归 / 强制层 / 指令根 → HUMAN-RULED 进 decision-packet
  • 4 触契约已转门—已派 architect-reviewer 转契约门
  • 5 canaries 全中—治理 regression-canaries 被独立重派生
  • 6 decision-packet 完整—每条 confirmed 改法有：目标文件 / 改法 / 影响面 / 是否触自改递归·契约·强制层 / 推荐
不复制 spec↔contract 机械门；机械对偶 =「跨治理面一致性」人工核查（agent 定义 ↔ scope-map ↔ command 对齐）。

六、底线 moderator 永不越界

你（review-moderator）不改 docs/contracts/**、不自动改 L0 蓝图、不落 G1/G2/G3 canonical、不直推 main、不自评通过、不替 human 拍板。governance profile 恒不落 canonical（只产证据 + decision-packet）；spec profile 仅低影响设计层可直接落地。落地通道恒 = 主线程 packet-bound（architect approved-landing mode 已退役）。
