# Pod 复盘 · 260829-schedule-reminder（包 7 日程提醒全链路）

> 第一人称热记忆。测试数字、闸态、轮次、判定以机器制品与 pod-events 为权威，本文不复述、不冒充第二事实源。

## 一、我在这个 Pod 里说错过的话，比预想的多

三处，都是我自己复核时发现的，不是别人挑出来的：

1. 我判「V20 预合成那半边属 spec 措辞与裁定的口径差、不是契约差」，并向 human 这样说了。实际契约 §三 第二条 bullet 原文就写着「排程时预合成」。那行我在这次会话里**亲自引用过**——引用时没意识到它在讲同一件事。定性被 integrator 纠正、由 architect-reviewer 重新归到 CONTRACT_CHANGE_REQUIRED。**教训**：凡我说「这不触契约」，依据必须是我读过的那一行，而不是我对契约覆盖范围的印象。这一条对我这种编排角色尤其危险，因为「不触契约」=「不开闸」，误判等于直接省掉一道人工门。
2. 我登记过「与并行包冲突时以先入 main 者为准」。这条口径对 `mcp_server.cc` 那种真重复修复是对的，但照搬到 `.v3` 版本化槽位就**有害**——因为假绿方向恰好是单边丢弃那一侧。我写那条注记时手上还没有并集实验数据，属于把局部正确的规则当通用规则用。**教训**：冲突消解口径要按「文件是什么性质」分列，不给一句通吃的话。
3. 我说过「设备构建承重闸绿了，那三行修复的价值当场兑现」。那是 `degraded:true` 的降级放行（未真编）。**教训**：任何闸的 `ok:true` 我都要连带读 `degraded` / `skip` 字段才能对外表述为「已核验」。planner.md 的 FS-EVIDENCE-2 只核证据有效性与布尔值，不区分降级——这一段得靠人兜，我已经把它写进给 integrator 的收口指令里。

## 二、亲跑数字这一条救了我两次

这个 Pod 里子 agent 有两次数字与实况不符：builder 报 host 计数少了一条红（并推测某条既有红「已转绿」），integrator 报某冲突文件「自动合并干净」而实际是冲突。两次都是我自己重跑一次命令、多看一次原始输出才发现的。成本都很低（一条 ELF 运行、一次 `git merge-tree`），收益是判读口径没歪。

**结论**：凡是要进合并门、进对外汇报的计数，我自己跑一遍；子 agent 的结论我信，**它的读数**我不代信。同时这不是不信任——builder 后来自己回头把运行目录口径统一了，integrator 也主动交出了它自己发现的、我原本不知道的危险。它们都诚实，误读是流程噪声不是品行问题。

## 三、本批最贵的发现是并行包抢 `.vN` 版本槽

两个包从同一 main 分叉、各自本地自增版本号，必然撞号；而版本化制品是「整份文件承载约定」，所以 add/add 冲突只有一边活。真正让我后背发凉的是它的**不可见性**：我们的 carrier 齿用了「备注」「学校课程表」这类宽词，main 版里也偶然命中，于是丢约定的一方照样绿。acceptance-author 顺着这条去做同源审计，又挖出同族的第二例（降级判据里 `-1` 逃逸支恒真），一处修复顺出两处同类病。

**下次 launch 阶段我就该问一句**：本包会写哪些版本化槽位、批内还有谁在写同号。这在 intake 是五分钟的事，在合并门是一次 rebase + 一条 ARQ。

## 四、我在流程上自己走的弯路

- 我一度把 mutation 测试当成「planner 亲自跑闸后的活」。实际 planner 对 `firmware/**` `server/**` 是 deny，且 `mutation-check` 文件头写着变异由 verifier/fixer 执行——绕一圈发现只能派回 builder。intake 时读一遍闸脚注能省掉这段。
- 我把一条 planner 侧的过程注记错登成 `human-decision` 事件类型，并在回报里写过「两条裁定已入册」——那一刻审计面会误读成有人批过什么。已追加自纠指针。闭集事件类型里缺 `planner-decision` 位是结构性诱因，已进 ARQ 素材。
- 我给一次 Bash 直跑的闸补 stamp 时填了占位耗时，随后用 evidence 里的真实起止时间重记并留自纠注。占位数哪怕碰巧接近真值也是假据。
- intake 时 `current/taskpackage.json` 投影还指着上一个包，而 `verify.mjs` 按它解析 TaskPackage——不刷就会拿别人的包做判定。这是共享投影的既知结构问题，但它落在**我这个会话**里就是静默假绿，不是抽象风险。
