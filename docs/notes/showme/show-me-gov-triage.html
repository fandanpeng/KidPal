Triage 前置门 · /triage-change 逐步拆解

变更开工前的分流前置门——不是只判包大小，是分面路由器：变更进来先四面探测（intake），产出 facePlan 决定哪些面要动、按什么顺序动，然后扇出最多四条 flow（需求 / 架构 / 契约 / 实现，各面跑各自的完整流程和门），实现面才判四档拆包。
变更进来 → 四面探测 intake（本篇第①步） ｜需求面那格→ 需求三档流程 ｜升级判据→ 事实源侧 → Track B 默认 Track A 判据命中
主线程人类主会话 · 编排 + 落盘（不受 per-agent enforce-scope 限） architect只读 + 审 + 返回裁决，零写入 architect-reviewer逃生门四分类（契约预审） human人类触点（确认 / 冻结 / 起会话） planner / portfolio下一段 dev-loop 会话

零、一句话 what this gate is

它是变更入口闸，不是业务门。变更进来先做四面探测（intake）——按 change-intake.md 对照 requirements / architecture / contracts + CRQ 未结账 + governance 面逐面查触面事实（触面是查出来的，不是申报出来的）。触面 ≥2 → 建 spine（delivery/changes/intake/<changeId>.md），命中升级判据（触 docs/contracts/** / 跨系统结构性 / 存疑向严）→ 按 facePlan 分面路由：架构/契约面走 Track A / 契约门，实现面留本门继续分档，不再整单踢走；governance 面命中 → 路由 /arch-change 治理 profile；需求面那格 → 需求三档流程（requirement-change.md）；纯实现面 → 照旧判四档。统一 intake ≠ 统一门——四面门照旧各归各裁。
本门 convention-only（当前无机器牙齿，靠约定 + 多层人工兜底）。作者≠判官：architect 审 + 起草，FROZEN 归人类，落盘归主线程。

一、全景：一次 intake，扇出最多四条 flow

triage 不是只判拆分包大小。四面探测产出 faceMap + facePlan：哪些面要动 · 每面谁裁 · 什么顺序。之后按 facePlan 扇出——每个被触的面跑自己那条完整 flow（自己的角色链、自己的门），轻面在 triage 会话内联跑、重面 headless 拉起跑；每面定稿回填 spine anchor。「判四档拆包」只是实现面那条 flow 的第一步——把它当全部，就退回了升级前的旧门。
需求面 flow
human 裁意图 → story-author 起草 → requirement-reviewer 四查（否回循环）→ 档 2 加 human 终拍 → 落稿 + §9 版本行
↩ anchor: §9 版本号
架构面 flow
/arch-change（Track B 七步闭环 / Track A 对抗重路径）→ PROPOSAL → human FROZEN
↩ anchor: changeId

二、实现面那条 flow 的六步 facePlan 的实现面行怎么跑——其余面见 §一扇出，各跑各的

读法：下面六步是实现面 flow 的逐步拆解（含 intake 入口）。需求 / 架构 / 契约面被触时，它们的 flow 按 facePlan 顺序在别的会话跑（内联或 headless），不在这六步里——别把这条当成整个门的全部。
  1. 主线程输入 = plan / 想法→ 你是人类主线程编排者
    输入是 plan mode 产出的实现思路、一句话（如「修复线索 SSE 重复行」）、或一份 plan 文件路径。你按 .claude/references/change-triage.md 的程序推进，每步显式说明「派给谁、为什么、期望产物」。
  2. 主线程四面探测（intake）→ 触面≥2 建 spine；升级判据命中 → facePlan 分面路由；纯实现面 → 继续
    派 architect（只读 + 同会话 return）按 change-intake.md 做跨面探测：语料 = requirements（含 §9 账）/ architecture / docs/contracts/** / CRQ 未结账三域 / governance 面；触面事实是查出来的，不是申报出来的。产出 = faceMap + facePlan，主线程落盘 spine（触面 ≥2 时，建档前先查重既有 spine）。升级判据命中（触契约 / 跨系统结构性 / 存疑向严）→ facePlan 把架构/契约面路由 Track A / 契约门，实现面留本门继续分档——不再整单踢走；governance 命中 → /arch-change 治理 profile、不建实现面档；需求面那格 → 需求三档流程（requirement-change.md 档 0/1/2）。intake 收尾有唯一必停触点：立项 ack——四面对齐「为什么改 / 往哪改 / 改动多大」。
  3. architect派 architect 比例化 review→ 四档裁决 + reviewed plan（会话内，未落盘）
    派 architect（只读 + 审），按 change-triage.md 判四档 + 出 reviewed plan。architect 只审 + 返回（同会话 return，非跨会话 prose），不写任何文件。力度按档比例化：大 feature（③拆包）= 实质单轮 review（findings 逐条 + 处置），生成 delivery/workstreams/<ws>/review.md 内容（findings + architect sign-off）；小 feature / bug（②单包）= 快审（确认判据 + 路由裁决），裁决写进 plan.md frontmatter、不单独成件。
  4. human人类触点①：确认 / 改判路由→ 档位定稿（落盘前必过）
    用 AskUserQuestion 呈现 architect 的四档裁决，人类一句话确认或改判（如 Lite→Full）。落盘前必须过这一关——Lite/Full 是安全相关判断，architect 误判需人类 backstop。
  5. 主线程主线程落盘（只搬运，不改内容）→ 三个落点之一
    按确认后的档位把 architect 的 reviewed plan + 裁决原样搬进它的家（主线程不受 per-agent enforce-scope 限）：
    · ③ 大 feature → delivery/workstreams/<ws>/PROPOSAL.md（+ review.md），frontmatter freezeState: pending-human；按 WORKSTREAM-PROPOSAL.template.md（三问 + 分型）起草，业务目的清单 / workType 数组 / spec 关系标注三项硬项缺失会在 portfolio-planner intake 被 fail-closed 打回。<ws>/ 目录由你（人类/主线程）创建 = 「设计权威落家」。
    · ② 单包 → delivery/taskpackages/<id>/plan.md，frontmatter 含 rigor / riskTier / sourceType / reviewed-by / date；建包时按 task-intake-and-slicing.md 创建 taskpackage.json + 填 origin（upstreamType / upstreamRef / upstreamFrozen / workstream）+ 注入 YYMMDD- 日期前缀 changeId + 写 planRef 指回 sibling plan.md。
    · ① 直接修 → 不落盘（地板：不改 apps 行为 / 人类明确跳过）。
  6. human人类触点②：仅大 feature 冻结→ FROZEN PROPOSAL（版本 / sha）
    人类盖 FROZEN。作者≠判官：architect 不能自冻（scope 机器兜住——architect 的 allow 不含 delivery/workstreams）。portfolio-planner 只拆 FROZEN 的 PROPOSAL。
  7. human人类触点③：报告下一步命令（runbook）→ 按 facePlan 顺序，human 起对应会话
    按 facePlan 顺序打出各面执行命令——轻面注明内联执行（本会话继续一级派发），重面给出 headless 拉起命令（claude -p 完整顶层会话，显式 --agent + 匹配 settings + changeId；到人类门即停，禁递归、禁跨门，纪律见 change-intake.md 三铁律）。下游会话开场先读 spine 的 faceMap/facePlan，不要求 human 重述意图。实现面命令映射保留：② 单包 → planner 跑 /build-feature <id>（从 plan.md 读 reviewed plan 做 intake）；③ 大 feature → portfolio-planner（指 <ws>，从 PROPOSAL.md 拆包）。headless 拉起的是完整顶层会话（非子 agent），「子 agent 不能再派子 agent」约束不变；dev loop 关键人类门 human 仍必须在场。

三、四档裁决 实现面 flow 的分档：architect 判 → human 确认 → 三个落点

③ 大 feature · 拆包
实质单轮 review → workstreams/<ws>/PROPOSAL.md + review.md（pending-human）→ human FROZEN → portfolio-planner 拆成 N 个带依赖的 TaskPackage
② 单包 · Full
快审（确认判据 + 路由裁决）→ taskpackages/<id>/plan.md（rigor=full）→ planner 跑 /build-feature
② 单包 · Lite
快审 → taskpackages/<id>/plan.md（rigor=lite）→ planner 跑 /build-feature。Lite↔Full 误判由触点① + supervisor 兜底
① 直接修
不落盘。地板：不改 apps 行为 / 人类明确说跳过流程（须诚实记录「跳过流程」）

四、逃生门（reviewer-first）review 中发现疑似触事实源

本门无权批准

architect-reviewer 疑似触契约 / spec / agent 定义 / gate

review 中发现疑似触事实源 → 先派 architect-reviewer 四分类（不自己判、不继续落盘）。四分类结果决定去向：
CONTRACT_CHANGE_REQUIRED转契约门 + 停，升级 delivery/changes/arch/（本门无权批准）
SPEC_CONTRACT_DRIFT同上：转契约门 + 停 + 升级
NO_CONTRACT_CHANGE / IMPLEMENTATION_ADAPTER不触契约 → 回本门按四档继续
intake 前置后逃生门仍在：四面探测已把跨面触面前置折叠进 facePlan，但 review 中仍可能新发现疑似触面（探测漏网 / 改着改着触到）——reviewer-first 逃生门保留兜底，处置不变。

五、spine 制品速览 统一 intake ≠ 统一门

制品形态（delivery/changes/intake/<changeId>.md）

  • 一变更一文件、lane 中立；写者恒 = 主线程（anchors 回填也是）
  • frontmatter 七字段：changeId / sources（human 意图原话逐字）/ faceMap（四面触面事实 + governance 命中行）/ facePlan（各面谁裁 + 顺序 + grilling 一次收敛）/ anchors（per-face 回填槽）/ openQ（疑问裁定留痕）/ status
  • 各面 changeId 映射：req = §9 版本号 · contract = packet · arch = changeId · imp = taskpackage id

状态机与冻结语义

  • intake → in-flight → awaiting-human:<gate> / awaiting-upstream / awaiting-human:<openQ> → closed
  • spine 免冻——它是路由账本不是设计文档；冻结语义由各面制品承载（§9 版本行 / 契约 packet / FROZEN PROPOSAL / origin.frozen），anchors 只记冻结事实
  • launch 前置：facePlan 中先于实现面的各面 anchors 未回填 = 上游未冻结 → 实现包不得 launch
  • 疑问三级处置 L0 就地 / L1 主线程 / L2 呈 human（存疑向严）

六、关键不变量与边界 convention-only

convention-only 不变量（当前无机器牙齿）

  • 主线程只搬运 architect 的 reviewed plan，不改内容
  • 单向守卫（riskTier overrides rigor）靠人类触点① + supervisor riskTier 升级兜底
  • FROZEN 拆包门靠 portfolio-planner 自觉
  • plan.md planner 只读消费，改需留痕
  • 机器守卫记 ARQ 后续 G3（见 change-triage.md）

门的性质与红线

  • Part-2 工程门 / bootstrap 临时信任门（权威在 K9 §11），不是业务门、不进 DEV-GOVERNANCE §5 六门清单，与业务运行时 6 门无涉
  • 你不改 docs/contracts/**、不改 L0 蓝图、不直推 main
  • 升级判据命中 → facePlan 分面路由（架构/契约面走 Track A / 契约门，实现面留本门分档）；governance 命中 → /arch-change 治理 profile；需求面 → 需求三档流程
  • 对偶：统一 intake（四面探测 + spine）折叠跨面 · 各面门照旧各归各裁——统一 intake ≠ 统一门
