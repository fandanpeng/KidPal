# write-story · KidPal story 撰写纪律

Story 是需求面的最小承重单元。它回答「产品是什么」，永不回答「怎么造」——后者归 architecture.md。

## Story 结构（五件，顺序固定）

```markdown
##### S-Fx.y · <标题>

> 作为<角色>，我希望<能力>，以便<价值>。

**验收标准**（Given/When/Then，正常 + 边界 + 异常至少各一条）
- AC1：Given <前提>，When <触发>，Then <用户可感知结果>
- AC2：……

**线框**：WF-Fx-NN 标注②③（线框实体随 feature 节；待补写「线框待补（归设计稿迭代）」）

**补充规则**：字段校验 / 权限 / 数据口径 / 埋点 / 文案（无则写「无」）

**锚**：UI = `canvas-pX`（舞台粒度；0–3 个为本 skill 新增经验上限——超出先自问是否锚了「道具」或 story 该拆，非锚行规则六条既有条款）｜ 支撑 = arch §x.y ｜ 可行性 = ✅/🟡/🔴
```

- **ID**：`S-Fx.y`——F = Feature 编号，y = feature 内序号；发布后稳定，不回收、不复用。
- **角色**：孩子 / 家长，二选一站稳；一条 story 只服务一个角色视角。
- **线框编号**：`WF-Fx-NN`（WF + Feature 号 + 两位序号），实体线框集中放 feature 节内，story 按编号 + 标注点交叉引用；线框管布局结构，视觉锚（data-od-id）管设计稿，两层不混。

## 撰写纪律（每条都对应一次真实翻车）

1. **业务框架强制**：story 原文必须「作为…我希望…以便…」三件齐。反例（真实，260829-schedule-reminder 包 story 字段）：「脑算网关推：OpenClaw cron（每 15 分钟定期重算 + QQ 录入即时触发）算三档时刻、幂等 id…」——这是技术方案，不是 story；对应真 story 是「作为孩子，我希望…设备提前主动提醒我，以便不丢三落四」。
2. **机制词禁令**：story 正文（原文 + AC + 补充规则）禁出现实现机制词——cron、散列、幂等、JSON、预合成、WebSocket、API、字段名。写到「怎么做」就停笔，搬去 architecture.md 或补充规则的「数据口径」（口径 = 需求语义，如「『今天』按本地日期零点切换」；格式权威在契约层，不复制）。
3. **AC 是业务可读的验收**：Given/When/Then 用人话写孩子/家长可感知的画面，覆盖正常 + 边界 + 异常；dev-loop 拆包时验收齿（Sx-Ay 形态）逐条回引 AC 号——AC 号就是 story 与验收测试之间的对账点。
4. **可行性诚实**：✅ = 有实测留档/包闭环证据；🟡 = 设计可行但关键环节未实测；🔴 = 当前架构撑不住。**🔴 必须同行挂开放问题或 ARQ 编号**，不许静默存在（Pod 无权自裁，处置 = 立项讨论）。
5. **改 story = 改需求**：编号不回收；砍掉的 story 进 requirements.md 文末「已砍清单」（§8）并注明砍因与日期，不物理删除编号。
6. **NFR 回引**：story 内涉及的量化质量要求（延迟、断网、字号…）写成「具体场景的具体化 + 回引 NFR-ID」，同一约束全仓只在 NFR 章（requirements.md §5）定义一次。

## 锚行规则（本 skill 为 SSOT；2026-09-13 自 requirements.md 文件头部迁入）

锚行三件 = **UI**（设计稿舞台锚）+ **支撑**（`arch §x.y`，指向 architecture.md 真实小节，小节编号发布后稳定）+ **可行性**三态（✅ 已实证 ｜ 🟡 设计可行·待实证 ｜ 🔴 当前架构撑不住）。UI 锚六条：

1. **粒度**：锚「舞台」——页面画布（`canvas-pX`）与会话状态（`state-*`）；不锚「道具」——图标/字体/组件级资产（`icon-library`/`font-*`/`comp-*`）由设计与实现侧引用，story 不挂。
2. **共享**：跨 story 的状态链在 requirements.md 共享底座（§2）钉一次，story 引「共享底座」不重复罗列。
3. **例外**：组件本身是 story 的验收对象时才单锚（如成就盖章 `comp-stamp`）。
4. **指向**：锚引用指「docs/ui/ 现行设计稿」语义，版本更迭只改本行一处；当前 = [kidpal-ui-design-v3.html](../../docs/ui/kidpal-ui-design-v3.html)。
5. **设计稿锚稳定规约**：`data-od-id` 是约定不是保证——id 只增不随便改，改名/删除 = 有意识的锚维护动作，改设计稿者负责同步 story 引用；出新版设计稿时跑 `node .claude/scripts/spec-anchor-check.mjs --diff-ids <旧设计稿> <新设计稿>`，被 story 引用而消失的 id 必须显式处置（同步改锚或恢复 id），不许静默断。
6. **机检**：每个 UI 锚必须解析到现行设计稿真实存在的 `data-od-id`——`node .claude/scripts/spec-anchor-check.mjs`。

## 完稿自检（写完逐条过）

- [ ] 「作为/我希望/以便」三件齐，角色单一
- [ ] 正文零机制词
- [ ] AC 覆盖正常 + 边界 + 异常，全部业务可读
- [ ] 线框引用或「待补」占位在场
- [ ] 补充规则无格式复制（契约面内容只写口径）
- [ ] 锚行三件齐，spec-anchor-check 绿
- [ ] 🔴 有挂账引用；🟡 写了待验什么

## 边界（不归本 skill）

- 拆包时「TaskPackage 必须内嵌 story 原文 + 验收齿回引 AC 号」的转写规则 → 拆包链治理（260912-gov-review-portfolio-decomposition-chain）。
- 架构怎么支撑 story → architecture.md；契约格式 → docs/contracts/**（契约门）。

## 模板应用例（S-F1.4，与 requirements.md 现文一致）

```markdown
##### S-F1.4 · 日程提醒

> 作为孩子，我希望遇到非常规的事（要带的东西、临时安排）和容易忘的课
> （周末培训班这类）设备提前主动提醒我，以便不丢三落四；
> 例行去上的学校课我自己看课表就行。

**验收标准**
- AC1：Given 录入了明天要带画具的美术课，When 今天 20:30 到点，Then 设备提示音 + 语音读出提醒文案 + 弹窗驻留（大字事项 + 时间），弹窗驻留到按键
- AC2：Given 弹窗驻留中，When 按 KEY，Then 关闭回当前页；When 按 BOOT，Then 关闭并照常翻页
- AC3：Given 弹窗期间另一条提醒到达，When 收到，Then 排队不叠屏；当前弹窗关闭后下一条自动弹出
- AC4：Given 同一提醒已弹过，When 云端因重算/重推再次下发同一提醒，Then 设备不重复弹窗
- AC5：Given 设备断网，When 到点，Then 无提醒——设备不缓存事项（回引 NFR-OFF-1）

**线框**：线框待补（归设计稿迭代）

**补充规则**：范围口径 = 「学校课程表」区块不提醒（在校例行）；「每周固定课表」+ 一次性安排走三段阶梯；
三档时刻 = 前一天 20:30 / 当天 07:45 / 事前 15 分钟（全局常量）；权限 = 录入仅家长侧，设备端只读

**锚**：UI = `state-reminder`（v3 设计稿实存 id）｜ 支撑 = arch §2.9（提醒调度与推送机制）、§3.1（UI 实现策略·弹窗渲染） ｜ 可行性 = ✅
```
