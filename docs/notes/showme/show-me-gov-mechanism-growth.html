五个典型跟头 —— 从摔到长的完整过程

每张卡 = 一次完整的成长循环：机制在 → 问题现 → 骨头长。

诞生问题长骨假绿验收 → 判别力闸

机制在07-12 首战：10 个冻结 TaskPackage 走完 dev-loop，全绿交付。
问题现验收测试「没报错就算过」——同一缺陷在两次全绿里溜过，夹具根本不落在差异上。
骨头长07-31 acceptance / unit 两闸补判别力：「断言必须真实结果」；后来沉淀为常驻纪律「反转实现必须变红」。

判官死循环 → 熔断换判官

机制在对抗 review：challenger 出 findings、defender 答辩、adjudicator 裁。
问题现09-09 input-surface-frontload：同一判官 R1→R3 三轮 NEEDS-WORK，反复拉扯烧 token 无进展。
骨头长熔断入规：3 轮未 GREEN → human 三选一。首战选「换新判官再战 1 轮」——零上下文新实例 R4 直接 GREEN、零 findings。

运动员兼裁判 → 纯判官原则

机制在architect 战略设计 + 评审 + 起草，能力最强的角色什么都干。
问题现既起草又 landing：自己写的方案自己落，对抗形同虚设。
骨头长09-06→07 定死：architect 恒纯判官 / 起草、永不 landing；landing 通道恒 = 主线程 packet-bound 一条。landing-verifier 独立核验补 builder≠verifier 对偶。

retro 凉了 → 先于合并

机制在Track B 七步闭环里 retro 是第 7 步——合并之后才写。
问题现合并完心智已切换，教训记录流于形式，「趁热写」落空。
骨头长08-26 retro-before-merge：七步 6↔7 对调，retro 成为合并前置。之后每批制品四件套 = PROPOSAL + landing-summary + landing-verdict + retro。

合并必死 → 修法回流

机制在merge-driver 自动合并 Pod 分支——治理机器的自动化骄傲。
问题现Pod worktree 拓扑下 `git checkout main` 必被拒（main 被主 checkout 持有）——07-15 首修没修死，KidPal 迁移后又实测复现。
骨头长KidPal 09-06 根治 + 拓扑自检；09-07 源仓逐条实测「确认同病」后以它自己的 Track B 评审回流。治理 bug 的修复本身走治理流程，形成双仓循环。

三个月长出来的四条规律

摩擦驱动，不预想问题

上面每个 ✗ 都是真实卡壳的现场记录，没有一个机制是「提前设计」出来的。设计只发生在问题实测复现之后。

最贵的学费都交在「闸说谎」上

假绿（vacuous green）与假阳（fail-open 的 FP）清算贯穿 7→9 月，是投入批次最多的单一主题。闸宁可 fail-closed，不可装作在岗。

分权是结构性的，不靠自觉

builder≠verifier、判官≠landing、scenario 冻结 charter 后 challenger 只读、human 只在两个判断点出场——每次越权都长出一条机械边界。

治治理，用治理

治理自身的 bug 走同一套 Track B 评审；回流到他仓也要先「确认同病」再走对方的闭环。机器修自己，用的正是自己的规程。
