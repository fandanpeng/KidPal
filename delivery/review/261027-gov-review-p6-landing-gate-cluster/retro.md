## 3. 摩擦与卡点（按痛感顺序）

- **F1 · 落地 staging 两连漏**：现象 = 主线程 git add 把两条已结 ARQ 的归位新路径写漏 `_archive/2026/` 前缀（staged 只有删除态、无新增态），commit 前 staged stat 复核抓回 → 根因 = 归位移动件的 staging 是「删除 + 新增」成对操作，凭记忆列路径易漏一半 → 证据锚 = 本主线程执行记录（首次 staged stat 12 件中无归位新路径）。
- **F2 · 复跑全套税**：现象 = v0.2 改稿轮为四项文本级修订复跑全套沙盘验证（369K）；主线程落地后同样全套复跑 → 根因 = PROPOSAL §5 未区分「全量复跑」与「影响面窄化复跑」档位 → 证据锚 = 改稿轮 tokens 369K（时间账表）。
- **F3 · ADVISORY-1 V5 措辞字面**：现象 = summary 写「review 目录仅余 PROPOSAL.md」时 summary 本身尚未落盘，字面自指不准 → 根因 = summary 写作时序自指：写「目录里有什么」的句子时作者自己还没进目录 → 证据锚 = landing-verdict ADVISORY-1。
- **near-miss（最险一刻）**：V2 归档位兜底——两条已结 ARQ 归位后，V2 的 append 断言若没有归档位兜底就会假 RED（checked 19 / missing 2）；兜底把「条目归位移动」从假红变如实回报（归档路径逐条列明）——本批自己修的机能在本批自己落地时被消费，闭环成立；若未修，落地验证当场炸。

## §4 优化建议（按 ROI 排序）

1. **复跑分档义务**：治 F2 · 载体 = ARQ 收件箱（登记「PROPOSAL §5 验证集应区分全量复跑 / 影响面窄化复跑两档，改稿轮按影响面复跑」）· 遗憾收益 = 改稿轮 ~200–300K/批。
2. **归位件 staging 配对清单句**：治 F1 · 载体 = 登记不硬治（并入 ARQ-261027 的脚手架/落地纪律讨论面：装配落地序列 checklist 句「归位移动 = 删除 + 新增成对 stage」）· 预期收益 = 省一次 staged 复核返工。
3. **summary 自指句时序纪律**：治 F3 · 轻（NIT 级），登记不硬治。
