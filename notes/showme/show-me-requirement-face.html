需求面变更流程 · story-author + requirement-reviewer（讨论稿 v2）

v2 变化：需求面自立流程、不再借 /arch-change（结构性档也不走对抗机器）；新增 requirement-reviewer 角色，作者≠审者成对偶。分工 = 语义档 author 写 + reviewer 审即收；结构档 author 起草后 architect 判「能不能实现」、reviewer 查「写没写准」。
human需求意图的唯一来源与终裁（事前裁意图；档 2 终拍） story-author（新）起草：按 write-story 纪律写修订 + 自检 + 撞车扫描，只起草不裁定 requirement-reviewer（新）审：写准没有 + 纪律合规 + 撞车复核 + 锚机检；只审不写 architect仅档 2 出场：可行性判断（能不能实现）+ 影响面，只出意见不裁定语义 主线程派发 + 落盘 + §9 记账

专用变更流程 · 三档 谁出场看档位

档 0 · 勘误 / 措辞不改语义：错字、排版、表述澄清、锚行格式
human 指出一句话指错
↓
主线程 直改过 write-story 自检 + 锚机检
↓
§9 记账标「勘误」行
无新角色，reviewer 也不惊动——机检兜住格式面。
档 1 · 语义修改AC 增删改 / 补充规则口径 / 单 story 内行为变更
human 裁意图改什么、为什么（原话即起草依据）
↓
story-author 起草全量读相邻 story 查撞车 + 完稿自检
↓
requirement-reviewer review对着 human 原话核对意图保真 + 纪律合规（五件齐 / 零机制词 / AC 三段式）+ 撞车复核 + 锚机检绿
↓ 不过 → 否回 author 重写（循环至过）
§9 定稿版本行 + changeId；落稿即收，无需再过别的门
author 写 + reviewer 审 + 落稿，三步结束。不触 /arch-change。
档 2 · 结构性story 新增 / 重写 / 砍除、跨 story 连锁、NFR 变动、Epic 级
human 裁意图结构性改动意图 + 取舍倾向
↓
story-author 起草含牵连面清单（关联 story / §2 底座 / 线框 / 路线图）
↓
architect 可行性判断这个需求能不能实现：可行性三态 + 实现代价 + 影响面；只出意见、不裁语义
↓
story-author 按可行性修订🔴/取舍点 → 升回 human，不带病下行
↓
requirement-reviewer 查写准牵连面改齐没有 / 意图保真 / 已砍清单登记 / AC 编号稳定 / 锚行批量改齐
↓
human 终拍architect 可行性结论 + reviewer 报告一并呈；拍板 → §9 定稿
architect 管「能不能」、reviewer 管「准不准」、human 拍「要不要」。

两个新角色的分工边界 作者≠审者

story-author · 只起草

对 human 意图负责：把原话转成五件结构 story 修订；跑完稿自检 + spec-anchor-check；全量读相邻 story 出撞车报告；档 2 额外出牵连面清单。不自评通过、不裁定语义、不拍板落稿。

requirement-reviewer · 只审不写

四查：① 意图保真（对着 human 原话逐条核）② 纪律合规（write-story 完稿自检全项 + 锚机检绿）③ 撞车复核（独立重扫相邻 story，不信 author 的报告）④ 牵连面完整（改了 A 处、B 处同步没有）。产出 review 结论 + 否回项；不代笔改稿，改稿回 author。

定稿载体与下游消费 冻结的不是文件，是「版本行 + changeId」

本批 · 需求面基建

入口不变：human 对主线程说需求（现状），判据与角色先行、triage 后接线。
  • story-author agent 定义（起草角色 + 自检 + 撞车扫描）
  • requirement-reviewer agent 定义（四查 + 否回权 + 不代笔）
  • 需求面三档判据 + 流程（落新 reference，triage ARQ 批来消费）
  • 定稿载体纪律（§9 版本行 + changeId 必带）
  • REQ- 域 CRQ 闭环纪律（owner + trigger + 销行条件必填）

下一批 · triage ARQ（ARQ-260928）

triage 升格为跨面申报后，把需求面流量路由进本批定的通道。
  • intake 四面申报 + 跨面分面计划
  • 消费三档判据 → 需求面那格指到档 0/1/2
  • launchPreconditions 推广到②路径（消费定稿载体）
  • /arch-change 退役安置（governance / spec 剩余流量归 triage 统一路由，另立变更）
关于 /arch-change 退役：本批起需求面变更不再依赖它（档 2 也不走对抗机器）；但 governance 面（agent 定义 / gate / 指令根）与契约预审现在仍由它承载，本体退役是独立治理变更，归 triage ARQ 批把 triage 升格为统一路由时一并安置，本批只做到「需求面摘出去」。
