## 0. 想实现的效果与差距

**目标效果一句话**：设备带着 TF 卡独立运行（不接串口、没有人在工位守着 COM5）时，事后也能把「那一刻板和云端之间到底发生了什么」捞回来看——板端自身的诊断日志常开、有界地落在 SD 卡上，供事后回看与排障（真机长尾：课表幻觉 `TECH-261018-schedule-read-compliance-residual`、ASR 误听）。

**现状差距**：架构目前只把设备日志当「串口流」（`docs/architecture.md:330` 三日志源之一：设备串口 COM5，被动 watch / 复位捕获纪律）；串口是现场有人在场的通道，设备脱离串口独立运行时日志即丢。同时决策 24 的介质禁令白名单（`docs/architecture.md:417`）与 §2.4 原则 5（`:101`）只开了「story 正文只读镜像」一个窄例外，其余「业务数据」仍不落板，且禁令枚举里的「日志」一词从未消歧——若不显式写明「设备诊断日志」是白名单第二项、并指明禁令中的「日志」= 业务日志，本批的实现承载包在 reviewer 四查③撞车复核处会被照旧按「日志不落板」打回。

**立项沿革（human 2026-10-18 原话逐字，必须作为本批的叙事定位被读到）**：

> 以前由于我们没有 TF 卡，设备的 RAM 存储有限，所以不记日志。现在有 TF 卡了，我们可以记日志了。这是在往好的方向变，并不是原来架构改了什么东西，只是原来受限，现在不受限了而已

**叙事定位**：本批是**约束解除**，不是架构原则变更。介质禁令的原始动因是当时的存储成本约束（未用 TF 卡、RAM 存不下），这一点决策 24 的「史实更正 + 窄例外」注记（`:417`，2026-10-17 随 `261016-p3-story-body-sd-cache` 落）已经写明；本批沿同一叙事把「设备诊断日志」补进白名单，不新立原则、不改「哑终端」定位、不改离线边界。

**非目标（本批不做，防 scope creep）**：

- **实现面不在本批**：`sd_log.c` / `sd_log_fs.cc` / `main.cc` 安装 `esp_log_set_vprintf` 钩子 / 板级挂载成功处 attach / `max_files` 5→8 / 两处 CMakeLists 登记，全部归 dev-loop **②单包 Full**（reviewed plan 已冻结：`delivery/taskpackages/261018-sd-log-persist/plan.md`；launch 硬前置 = 本 PROPOSAL FROZEN + landing）。

- 契约面不动：无 wire / API / display 响应块 / 课表 MD 结构变更；不新增远程开关或控制消息（四分类结论 `NO_CONTRACT_CHANGE`，见 §3 / §4）。

## 2. 问题、根因与改法（T1…T8）

### T1 · 决策 24 白名单增列「设备诊断日志」+「日志」口径消歧

**问题**：决策 24 的介质禁令白名单只允许设备凭证与服务器地址、预栅格化资产与字体、固件本体，2026-10-17 的窄例外只给了 story 正文。设备诊断日志（板端自身运行日志落 SD 卡）按现文本落在「其余业务数据」里，与白名单冲突；且禁令枚举中的「日志」一词在三条重述点（决策 24 / 原则 5 / §6.2）都未与「业务日志」消歧——实现承载包会被 reviewer 四查③照旧按「日志不落板」打回。

**证据**：
- `docs/architecture.md:417` 决策 24 句尾逐字：「**边界不变**：提醒 / 课表 / 日志等其余业务 / 身份 / 事项状态仍只驻 RAM、禁落非易失介质；「离线边界（断网无提醒）」部分语义不变。」
- `docs/architecture.md:101` §2.4 原则 5 句尾逐字：「提醒 / 课表 / 日志等其余业务数据仍不落板——此例外**只给 story 正文**、不扩及任意业务数据。」
- 业务日志口径出处：`docs/requirements.md:676`「家长知情权由 OpenClaw 侧完整日志兜底（对话与数据出网路径本就有日志，随时可查）」；`docs/requirements.md:624` NFR-OFF-1 邻位注记「『设备不缓存任何事项』（指提醒 / 课表 / 日志等业务事项）」；`docs/architecture.md:47`「家长知情权 = OpenClaw 侧完整日志」。
- 设备日志现状仅串口：`docs/architecture.md:330`「三日志源：设备串口（COM5，被动 watch / 复位捕获纪律）…」。

**根因**：介质禁令的原始动因是存储成本约束（决策 24 史实更正注记已载），而「日志」一词在禁令文本里一直只是业务日志（家长知情权）的顺带枚举；设备诊断日志此前不存在——无卡时代只有串口流、不落任何介质，所以既从未被显式排除、也从未被显式允许。TF 卡能力 2026-10-16 就绪后，这一空白变成实际冲突。

**改法**：在决策 24 条目句尾再 append 一段「白名单增列 · 设备诊断日志」注记，沿用决策 19 / 21 与 2026-10-17 story 注记的句尾补注先例（原文一字不动）：增列白名单项、写明形态边界（常开 + 有界轮转 + 目录总量 16MB 封顶 + 可删除）、做「日志 = 业务日志」的口径消歧、重申离线边界与提醒 / 课表不落板不变、并载明 human 对「含对话原文」的隐私接受。逐字插入段见下方围栏。

```text
【插入 · §10 决策 24 条目句尾 append（现有「边界不变」句之后）】

**白名单增列 · 设备诊断日志（`261018-sd-log-persist`，2026-10-18）**：介质禁令白名单再增列**设备诊断日志**——设备自身运行日志（固件 `esp_log` 输出流），常开 + 有界轮转、目录总量 16MB 封顶（512KB × 32 个文件）、可删除；写者 = 固件低优先级写盘任务。它是**可观测性数据**：不承载任何业务状态、不供掉电恢复、不是业务真相源。**口径消歧**：本条目与原则 5 所列「提醒 / 课表 / 日志等其余业务数据」中的「日志」指**业务日志**（家长知情权 = OpenClaw 侧完整日志，§1.3 / requirements §7 开放问题 3）——业务日志仍不落板、语义不变；设备诊断日志属**架构 / 运维面**概念，不在该业务数据枚举内。**边界仍不变**：提醒 / 课表等其余业务 / 身份 / 事项状态仍只驻 RAM、禁落非易失介质；「离线边界（断网无提醒）」语义不变——诊断日志不提供任何离线功能。**隐私接受**：落卡内容含**对话原文（STT / LLM 转录与回复）**，human 2026-10-18 有意识接受；与 `TECH-261016-sd-story-confidentiality` 同族（儿童数据明文落可拔卡）、暴露面加宽（全部对话转录 vs 孩子主动录的故事），隐私记账见该 tech 条目。
```
