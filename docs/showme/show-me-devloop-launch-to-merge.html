Dev Loop 全程：从 launch 到合并

事实核实于 2026-09-24（本机实测 board .git/devloop/pods/*.json：40 个 Pod · merged 36 · running 1 · blocked 1 · queued 1 · abandoned 1；逐字对照 build-feature.md / kidpal-pod-launch-prep skill / merge-driver.mjs / pre-merge-escalation-gate.mjs / hooks/verify.mjs）

零、一句话 the whole thing

一个包（TaskPackage）的一生：portfolio-planner 把它拆出来、commit 到一条专用 base 分支 → 主线程把它的 launch 面备好（worktree + 环境 + 图索引 + 启动卡）→ 人在那棵树里跑一个交互式 planner 会话 → 该会话（Pod）内部走「先冻验收 → builder 实现 → verifier↔fixer 磨到绿 → integrator 收拢」→ planner 拿机械合并门 → 前置升级闸放行后自动落本地 main；remote push 始终是人的事。
全程 5 段、1 个回路；合并是串行的（merge token + mergeOrder），Pod 之间并行上限 3。

二、② launch 面准备 launch 前，主线程备场 · 手册 = kidpal-pod-launch-prep skill

包从哪来：上游过 /triage-change 分档（拆包 / 单包 Full / 单包 Lite / 直接修），portfolio-planner 按 dependsOn + mergeOrder（WIP=3）拆成 N 个带 changeId 的包，制品 commit 到专用 base ref（非 main）。本段备的是「让它能被 launch」的场地：
1 调度判定dependsOn 全 merged ∧ mergeOrder 升序 ∧ WIP 余量 2 launch 机械门--check-launch 绿；上游已知红基线按「带锚三件齐」判停 3 worktree复用空闲树 ∨ 按需新建；一树一常驻分支 4 环境等价化镜像 sdkconfig / dependencies.lock + managed_components 软链 + bootstrap 5 专属图索引index_repository(worktree)——必办，不得降级「无索引、读文件」 6 board 预填pods/<id>.json 置 queued + worktreePath（running 归 Pod 自己） 7 启动卡launch-card.md，git-tracked，随 commit-before-launch 进基准 ref 8 记录交接progress.md 追加 → 启动卡交 human 自跑
launch 面不做什么（越权即事故）：不代跑 launch、不合并、不 push。launch 之后的一切（intake / builder / verifier / integrator / 合并门）归 planner Pod；跨 Pod 拆包与调度归 portfolio-planner；契约面归契约门。

三、③ launch 人在场，一树一会话

人在该包对应的 worktree 里自跑交互式会话（一个目录一个会话——并行同树在操作层不可达）：
# 在 Pod worktree 根目录下 claude --settings .claude/dev-loop.settings.json --agent planner
启动卡的五要素：
① 任务跑 <changeId>（workstream，mergeOrder N）
② 基线锚progress.md 带 SHA 行 —— 各面域判停结论（可引用 / 须重跑）
③ 上一包留根changes/dev/<上一包>/pod-retro.md，intake 逐条评估；构成 blockingDecision → fail-closed 上报
④ 固件严格模式VERIFY_FW_BUILD_REQUIRED=1（无关闭留痕即开）
⑤ 命令行身份探测 / 包事实 / 环境事实 / 教训全文一律不搬运，planner 凭 changeId 自探测四处
headless 路径暂不用：本仓 2026-09-24 human 裁定 launch 一律交互式（无人值守 headless 形态搁置，ARQ-260924 留 gov 批处理）。原因值得记住——headless 与交互式对 CLI 校验口径的容忍度不同，同一份 settings 在 headless 下会 exit 4 阻塞 dev/review-loop launch 面。

四、④ Pod 内 dev-loop 十步，由 planner 主线程驱动

planner 编排，全程主线程 · acceptance-author 冻验收 · builder 实现 · verifier 判（只读） · fixer 修 · integrator 收拢 · 机械闸 脚本
  1. plannerSource intake→ board queued → running
    先做 portfolio handoff 探测（两段契约）：按 changeId 找 taskpackages/<id>/taskpackage.json / devloop/pods/<id>.json / origin.upstreamRef → PROPOSAL。命中已存在的包 → 以其 sourceType/origin/rigor/riskTier 为权威消费，不重归一、不覆盖 sourceType。然后归一输入来源，定 sourceType / sourceRefs[] / riskTier / gateProfile[] / 子系统与 acceptanceRefs。信息不足就问人，不猜。
  2. 预审契约判定→ 触契约则停在契约门
    任何疑似要改 docs/contracts/** / events / schema / mcp-tools / shared-types / 系统 spec 的点，先派 architect-reviewer 预审。只有 reviewer 判定必须改契约时，才停在契约变更门交人类架构师。
  3. plannerSlicing / Planning 预检
    判 Lite TaskPackage / Full TaskPackage / 挂接已有 workstream / 新建 workstream / needs-triage。planningImpact=needs-triage 或 handoff blockingDecisions[] 未解决 → 停下，不得派 builder。开工前确认 .claude/scope-map.json 已允许本包的验收与实现路径，避免中途补 scope。
  4. plannerDraft TaskPackage→ delivery/taskpackages/<id>/taskpackage.json + current/
    必须立刻落盘，不能只在聊天里展示。条件升级触发器自检（触发形状只有 return / propose-drop / notify 三种）；notify 前须完成至少一次有记录的锐化尝试。非交互环境 AskUserQuestion 不可用时 fail-closed：写 pending-human-ruling.md 并以 needs-triage 退出。
  5. acceptance-author先写验收→ 冻结的验收测试 + 红基线
    产出冻结的验收测试（每条断言绑 TaskPackage 的 acceptanceRefs / sourceRefs，断言真实结果——DB 落库 / 事件发出 / 审计 / UI 状态，严禁「没报错就算过」），以及红基线命令与红基线结果。验收测试归 acceptance-author，builder / fixer 改不动。
  6. plannerFinalize TaskPackage
    补齐 acceptanceTestsFile[]、redBaselineCommand、redBaselineResult、docsSyncRequired、docsOwner: "integrator"，写回两处。缺任何一项、或缺落盘记录，不得派 builder。
  7. builder实现→ 冻结验收从红转绿
    在单个包边界内（apps/sX-* / 对应实现面）写实现与单元测试。只读消费 contracts 与 *.acceptance.*，绝不改它们；结构化日志带 correlationId。完成交回 planner，由 verifier 判定——不自评通过。
  8. verifier ↔ fixer内循环→ <changeId>/current/verdict.json（机器件，程序 fs-write，非 agent 落盘）
    planner invoke verify.mjs（dev-loop deterministic verifier）→ 拿 { ok, results, error }：
    · 绿 → 出循环，进第 9 步。
    · 红 → 把 error（ErrorEnvelope）交 fixer 打最小补丁（每轮聚焦一个 failingStep，避免散弹式改动）→ 再 invoke verify.mjs。
    · 直到绿，或满 3 轮 → 升级给人类（附最后 ErrorEnvelope + 试过的假设）。
    禁止嵌套派生——内循环由 planner 驱动。oracle 是对抗而非退出码：builder ≠ verifier。
  9. integrator集成 + 文档同步 + closeout 闸→ delivery/changes/dev/<id>/ 制品 + Review Packet
    全绿后收拢：docs-sync、架构 / 依赖卫生检查、安全证据收口、必要 ADR 归档、全量端到端（含跨子系统事件流），产出标准制品 + Review Packet + 可回滚路径。
    然后跑 closeout 闸 closeout-check.mjs --update-index（唯一授权的 closeout index projection 写路径）——缺三个 blocking 制品、milestones STATUS 漂移、workstream 缺失则红；verdict / verification 机器件缺失只 advisory。闸绿后在 feature 分支 commit 已绿改动（不 push、不在 main/master commit），供合并门复核已 commit 的 diff。
  10. plannersupervisor 合并门→ delivery/changes/dev/<id>/supervisor-verdict.json
    跑 supervisor-verdict-gate.mjs 机械闸（planner invoke，不派 supervisor agent）。输入必须含 TaskPackage source/risk/gate profile、verifier 证据、Review Packet、closeout 结果与已 commit 的 diff。判出 APPROVE / BLOCK / ESCALATE → 见下一节。

五、⑤ 合并门 → 落本地 main

机械闸

机械 supervisor-verdict-gate.mjs

判据 = 证据可信 + 风险等级。低 / 中风险且证据完整 → 机器 APPROVE 自动放行；高 / critical → 升级 human。
APPROVE继续走前置升级闸
BLOCK退回 fixer / planner；同一 changeId 连续 2 轮 BLOCK 未转绿 → 熔断 ESCALATE（不外环硬磕）
ESCALATE停下交人类 review / 合并（hd 计数主体 = 机械闸脚本）
必经，不是门

机械 pre-merge-escalation-gate.mjs · 前置升级闸

只重算「例外清单是否命中」，命中即 exit 1 并报命中项；放行 exit 0。它放行，merge-driver 才跑。
两档通用
  • diff 触 docs/contracts/** 且同批无契约门证据
  • 源 commit 落在 main / master 上（off-main 隔离被破坏）
  • 存在未 resolve 的 agent-escalation 或 blocked 态
dev-loop 档
  • riskTier ∈ {high, critical}（读 supervisor-verdict.json）
  • supervisor APPROVE 的 provenance 不可机验
merge token

机械 merge-driver.mjs --pod <changeId>

merge token 的 canonical consumer。串行化：按 mergeOrder 逐个处理，每个走完才轮下一个——所以合并是队列，不是并发的。
rebase 到 main→ quick-check→ merge→ 释放 token→ 下一个 Pod
rebase 这步顺带把该树常驻分支 rebase 到 main —— 树内治理面即为最新，所以下一包复用同一棵树可以直接续跑。
人批通道

human ESCALATE 之后的机械路径

人批后不停在口头：planner 落 pod-events 人批事件（payload.decision="approve-escalated-merge"）→ 再跑 merge-driver.mjs --pod <changeId> --human-approval-ref <eventId>，凭据透传给前置升级闸核验并进 merge commit message。
永不 push：入本地 main 是自动的（可回滚），remote push 始终由人经 PR 走。deny-main-push.mjs 钩着这条铁律。planner 也不直推 main、不改契约、不自评通过。

六、并行走多快 WIP=3 · 三棵树三个相位

并行发生在 ④——一棵 worktree 一个会话，三个 Pod 可以同时卡在流水线的不同段；但 ① 的依赖图说了算，⑤ 永远是串行队列（merge token / mergeOrder）。

buildingPod A

在 builder：让冻结验收从红转绿。产物还没成形。

磨第 2 轮Pod B

verifier 红 → fixer 最小补丁 → 再 verify。3 轮不进就升级人类。

排队等 tokenPod C

已 APPROVE + 升级闸放行，在 mergeOrder 队列上等前一个释放 token。

七、回路：这个 loop 会改自己

近端：Pod 收尾

planner 趁热写 delivery/changes/dev/<id>/pod-retro.md——本包的踩坑与摩擦。它是下一包 intake 的输入（启动卡第 ③ 要素），逐条评估，构成 blockingDecision 就 fail-closed 上报。

远端：跨 Pod 提共性

/loop-retro 周期性读多个 Pod 的复盘证据，提取共性踩坑 / 升级主题 / 流程债，把治理类发现转成 architect-owned ARQ——不自我批准、不直接开 TaskPackage。ARQ 走治理变更，改的是 ① 拆包调度与 ② launch 面的制度本身。
