# arch-doc-restructure · 架构文档新建/重构纪律

> 本 skill 沉淀自 2026-09-14 architecture.md 全量重构（342 行旧档 → arc42 十一节新档，26 处需求锚批改、机检归零）。适用 = 新建架构文档，或对既有架构文档做结构性重构；小修小补不适用。

## 一、基线与三条总则

基线 = **arc42 骨架 + C4 图法 + ADR 纪律**。动工前先对齐：

1. **单一事实源分工**（每类信息只有一个家，本档对其他面只放指针）：
   术语 → glossary.md；决策本体 → ADR.md；数据格式 → docs/contracts/；需求与阈值 → requirements.md；**本档 = 结构与机制**。
2. **内容归属三分法**（消除重复的钥匙）：
   机制**归属哪个组件** → 逻辑视图该组件小节；跨组件**怎么协作** → 运行视图对应场景；贯穿不变式（幂等/降级/重试上限）→ 横切机制。同一信息禁止两个家。
3. **as-is / to-be 显式分层 + 详略随风险**：现状描述与目标设计不混写；高不确定性处写深、确定性高的带过。

## 二、目标骨架（十一节，编号即机检对象）

| # | 章节 | 内容要点 |
|---|---|---|

| 2 | 架构总览 | 容器级总图（C4-L2）+ 顶层定位 + 架构原则（≤5 条）——先给全貌再展开 |
| 3 | 架构目标与约束 | QA 场景目标（可验证表述）/ 硬约束 / **假设清单**（被打破时的后果） |
| 4 | 质量属性→对策映射 | 表：每条 NFR 指到满足它的机制与小节——需求↔架构最重要接缝，不可缺 |
| 5.1 | 逻辑视图 | 组件/模块划分与职责（带代码文件锚）、依赖方向 |
| 5.2 | 运行视图 | 关键场景端到端时序（3–5 条，编号场景①②…，**编号一经锚引用即为稳定标识**） |
| 5.3 | 部署视图 | 设备/节点硬件表 + 拓扑（端口/证书/服务件）+ **运维面**（部署后核验、漂移告警、证书轮换）并入本节 |
| 5.4 | 数据视图 | 数据所有权/存储/生命周期表：位置、写者、生命周期、掉电语义、格式权威指针 |
| 5.5 | 开发视图 | 仓库结构/技术栈/构建烧录/测试基建/**UI 或实现策略**并入本节 |
| 6 | 横切机制 | 每条写清「在哪侧解决、为什么」：鉴权/离线/错误降级/重连/可观测性/幂等一致性 |
| 7 | 接口与契约 | 纯导航指针，细节一旦复制即腐烂 |

C4 层级与本骨架的映射：**L1 = §1，L2 = §2 + §5.3，L3 = §5.1，L4 = 代码本身（不画图）**。

## 三、素材挖掘（重构前必做）

架构文档最大窟窿通常是「实际做出来的东西没进文档」。挖掘源按优先级：

1. **部署面 README / 部署脚本**（服务、端口、证书、核验方式——部署视图与运维面素材）；
2. **dev 包证据**（`delivery/changes/dev/<包>/review-packet.md`、`deploy.md`——live 实证事实与遗留缺口）；
3. **ADR / 决策历史档**（已拍板的机制修正，注意 ADR 可能已推翻旧文档措辞——**以 ADR 为准**）；
4. **代码/图索引调研**（组件清单、常量、路径——用 CodebaseMemory 图工具或直接 grep；每条现状锚到文件级）；
5. **docs/notes/**（协议分析、实现策略、验证结论）。

挖掘产出 = 分组事实清单，**每条 = 结论 + 证据路径**；可疑数字/路径/名称一律回头机验原文，不凭转述落笔。

## 四、旧→新序号对应（锚批改纪律）

小节编号是 requirements.md 支撑锚的机检对象，改编号 = 有意识的批量动作：

1. **先落映射表**：旧 § 号 → 新 § 号逐行成表（含决策引用去向），存 `docs/notes/` 作为追溯地图——重构完成后保留，供考古旧文档引用。
2. **批改范围**：只改**活文本**；需求面/架构面的历史变更记录行按 append-only 纪律一字不动。
3. **决策引用去向**：`arch §5.1（决策 N）` 类引用拆成两部分——机制内容改指新机制小节，决策本体改指决策历史档（§10）或 ADR 编号。
4. **冻结历史档**：旧决策列表从 `git show HEAD:<旧档>` **逐字节提取**拼接（awk 区间 `/^1\. /,/^N\. /`），绝不手抄；历史档内旧自引用不改原文，在节引言加「自引用均指迁移前旧编号」注记。
5. **新编号约束**：新骨架必须覆盖 requirements 引用的全部 § 号；运行视图的场景编号（①②…）一旦被锚引用即为稳定标识，后续引言/注记不得错位。

## 五、脚本应用（spec-anchor-check.mjs）

`node .claude/scripts/spec-anchor-check.mjs` ——重构的三步闭环都用它：

- **正向三检**（默认）：① requirements 支撑锚 `arch §x.y` → architecture.md 真实标题（只机检 `##`~`####` 的编号标题 `N(.M)*`；「决策 N」引用不走机检，靠映射表保证）；② story UI 锚 → 现行设计稿 `data-od-id`；③ 可行性 🔴 必须同行挂开放问题/ARQ。
- **重构流程**：重构前跑一遍留基线 → 搭完骨架立即跑，拿悬空清单 → 按映射表批改 → **复跑至 arch 锚悬空归零**。
- **UI 锚悬空单列**：`char-window` 类错属设计稿面（docs/ui/ 缺 od-id），与架构重构无关——单独记账随对应改造消除，不混入本次验收。
- `--reverse`：反向视图（arch 小节 → 引用它的 story/NFR 清单），用于评估「动这节牵连谁」。
- 退出码 0 全绿 / 1 有悬空 / 2 用法错误；手动跑不挂 hook。

## 六、执行序（四步，各自可独立 commit）

1. **素材深挖**：按 §三 出分组事实清单；
2. **搭骨架迁移**：按 §二 骨架重写；每节头加「← 收编自旧 §x.y」保追溯；冻结历史档按 §四.4 逐字节迁移；
3. **锚批改**：按映射表改 requirements/其他引用方，`spec-anchor-check` 复跑至 arch 锚归零；
4. **glossary 新建/更新 + 互链核查**：新术语（含改名的新旧对照）落 glossary，双 spec 头部挂指针。

## 七、收尾自查清单（本仓实测踩过的坑）

- [ ] 文件路径、常量名、事件名逐条对源码 grep 核验（转述必漂移）；
- [ ] 「宣称已注记/已同步」处，原文里真的存在该注记（宣称≠事实）；
- [ ] 场景/列表编号与锚引用编号一致（引言补写时最易错位）；
- [ ] 预算/口径类数字标注「实测时点」，结构变更后旧口径要显式标过期；
- [ ] 历史档「冻结原文」与「指引性新注」分清，后者只进节引言；
- [ ] 通读一遍语言：生造黑话、中英混杂不当处交 design-doc-polish 复查；
- [ ] 全部改动按治理惯例如实记录（是否跳过 Track B 由 human 定）。
