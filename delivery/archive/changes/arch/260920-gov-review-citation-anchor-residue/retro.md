## 3. 摩擦与卡点（按痛感排序）

**F1【最重】· 自证式测量：拿待验对象自身当基线**。现象 = 我断言「四项硬编码已被派生集覆盖，可整条删除」，据此写成改法 1。判官 R1-F1 独立复跑证伪：现役 `citationPrefixes()` 以 `new Set(CITATION_BASE_PREFIXES)` **起手**，我拿一个**已经含这四项**的集合去验「四项是否被覆盖」——**同义反复，必然全 true**；去掉常量只跑两树递归得 walk-only **42 项且 `docs/`、`.claude/` 两个根都不在集**。**根因** = 测量设计缺陷而非计算错误：**测量基线与待验命题共享了同一个来源**。这条比「算错」更隐蔽，因为它产出的数字**看起来是实测的**、且会顺着进入改法（我的改法 1 直接据此写成「整条删除」，进而与改法 2 的回退分支自相矛盾）。**证据锚** = PROPOSAL §7 R1-F1（逐字）；重测命令与结果见 PROPOSAL §2 T1 证据段。

**F2 · 更正只改了一处、漏同步另两处**。现象 = v0.2 折入 F1 时，我校正了改法 1、改法 2、证据段三处，却漏了 §5 V7 的 `grep … 零命中（四项已删）` 与 §6 留根③ 的「四项硬编码已删」——判官 R2-G1 打回。**根因** = 本仓既有纪律「改单源判据时须 grep 其全部消费点逐一过」在**文本同步**场景下没被当同一条纪律使用：机械单源有 grep 可依，而**散落在散文里的同一断言没有索引**。**证据锚** = PROPOSAL §7 R2-G1；v0.3 修订表 + 我补做的三类词全文 grep。

**F3 · 用了早于定稿时点的实测数字（结构性，非疏忽）**。现象 = 两处同族：① V4b 的 headline「`problems` 29 条」是我在 v0.1 刚写完时跑的，判官 R1 复跑得 34、v0.2 定稿 39、v0.3 41；② §2 T3 子项 b 的夹具**描述**写「裸 `目标文件：`」而**实际夹具**路径带 backtick，导致引的 verbatim 与描述不自洽（判官 R1-F5 复跑得 2 条 findings、我只引了 1 条）。**根因** = 本类是「**实测体 PROPOSAL**」——它的证据段必须逐字回引畸形引据与计数，**于是文档每增删一次、它自己引的对象就变一次**。数字的时点与文档的定稿时点是**两个不同的时刻**，而载体没有区分它们。**这不是我偷懒**：v0.1 的 29 在 v0.1 时点是真的。**证据锚** = PROPOSAL §5 V4b 的漂移序列（29→34→39→41）；§2 T3 的两具夹具 verbatim。

**F4 · 核验官抓出未授权字符**。现象 = `abbreviated` 正则写成 `/[…»]|\.\.\./`，多发了一个 `»`（U+00BB），而 §2 T2 改法 2 只授权 `…` / `...`，其上注释亦只写这两式。核验官 landing-verdict A1 报出，并**实证** `»` 在全仓 PROPOSAL / `delivery/**` 零出现、对真实输入无行为影响（inert）。**根因** = 写字符类时凭手感扩展，而**冻结稿的授权面是逐字的**——inert 不等于「不算偏离」，本批要治的恰是「代码与契约不同形」。**证据锚** = landing-verdict A1；收敛后与 §2 逐字同形（复验第 1 项，含 byte dump）。

**F5 · 我自己的编辑事故：Edit 静默吞掉一行**。现象 = 执行 F4 的收敛时，我的 `old_string` 含尾随换行、`new_string` 不含，结果是**只删了那个换行、没改到字符**，并把 `abbreviated` 那行与 `const hits = ...` 行并成了一行。我当场从 `grep` 输出看出并修复。**根因** = Edit 工具的 old/new 差异语义——**当修改意图是「行内一小段」时，把整行连同尾随换行当作 old_string 会让「删除一个换行」也满足替换、从而产生看似成功的错改**。**证据锚** = 修复前后 `grep -n` 输出（可见两行被并）；核验官复验第 3 项确认末态**各为独立行、numdiff 维持 229/79**（若仍合并会 −1）——**这条之所以能被抓住，靠的是 numstat 这个独立于我的量**。

## 4. 优化建议（按 ROI 排序）

1. **【载体 = ARQ 收件箱（新）】「测量基线与待验命题同源」应进 PROPOSAL 的【硬项 · 起草期实证义务】。** 现该硬项已列「凡 regex / git / 机械门断言 → 草稿即附实测」「凡数字引用 → 现跑实测」等六条，但**没有一条问「你的测量基线是从哪来的」**。F1 恰恰满足现有全部六条（我真的跑了、真的留了痕），却仍然是同义反复。建议补一条：**「凡『X 已被 Y 覆盖 / 包含 / 取代』类断言，须声明 Y 的构造起点，并证明 Y 的种子集不含 X」**。预期收益 = 一次 BLOCKING 打回 + 一轮往返（本批 ≈12 min 子 agent + 主线程 ≈11 min 修订）。
2. **【载体 = ARQ 收件箱（新，或并入剩余计划 §1 的三条流程建议——同族）】「计数类断言的时点」须成文。** 实证 = 本批 F3：文档自身即被测对象时，raw 计数随定稿增删漂移（29→34→39→41），而核验官三轮复跑各得不同值（16 / 17）。建议成文：**凡被引对象就是本件自身 / 或随本件增删而变的量，一律降级为「性质断言」并显式标注「不作断言」，只在标冻前记录里留时点值**。预期收益 = 本批为此付了一轮 MAJOR 往返 + 主线程约 12 min 的数字对账。
3. **【载体 = 留批次（不硬治）】文本型单源断言没有 grep 索引。** F2 的根因是「同一断言散落在改法 / 验证集 / 留根 / 状态行四处，改动时靠人记」。机械单源有 `grep 消费点` 这条纪律，散文没有。**建议不硬治**——硬治需要给散文断言建索引，成本远超收益；务实做法是**在 PROPOSAL 标冻前检查里加一句「改某条判据后，对其核心措辞做一次全文 grep」**，载体 = 下次动 PROPOSAL.template.md 的批次顺带。
4. **【载体 = 本文件 + `/loop-retro`】Edit 工具的「行内小改」用法教训。** F5 的教训是具体的：**当只想改行内一小段时，不要用「整行 + 尾随换行」作 old_string**，否则「删掉一个换行」也会满足匹配而在语义上产生错改。同时 F5 也证明了一件事——**独立量（numstat 229/79）比自述更可靠**，建议把它当作小改动的常规自检。
5. **【载体 = `/loop-retro` 观察项】评审轮次的 meta 成本缺可观测面。** 本批三轮评审的 token 读数逐轮递增而时长递减，**口径不明**（累计 vs 单轮）导致无法判断「第三轮判 3 条 NIT 花 21 万 token」是低效还是误读。建议 `/loop-retro` 观察：判官 resume 轮的 harness 读数口径，以及「首次 BLOCK 后同实例 resume」是否比「换新实例」更省。

## 5. 一句总结

**两方独立结构接住了作者偏差，且各接住一次、互补不重叠 —— 这是本批最值得记的结论。** 判官在 drafting 期接住两次：R1 抓住**自证式测量**这条最隐蔽的作者偏差（它产出的数字看起来是实测的，且顺着进了改法），R2 抓住我第一次更正**自己的残留**（F1 的更正只改一处、漏两处）。核验官在 landing 期接住一次：A1 的未授权字符 `»`（inert、无行为影响，但属「代码与冻结稿不同形」）。**三次都不是「同一方重复抓同一类」**：判官抓的是**论证**、核验官抓的是**实现与授权的逐字同形**；判官两轮抓的也不是同一处（第一轮抓命题、第二轮抓更正）。⇒ **保险丝判定：有效**。另记一条**反向**观察：本批三轮评审**全部无升级 human 项**（T3 子项 b 的 `HUMAN_REQUIRED` 由 R1 判否、R2/R3 维持），即 human 在本批只出场两次（立项 ack + OQ 三裁）——**这正是 Track B 「human 只在两个判断点出场」设计的实证**。
