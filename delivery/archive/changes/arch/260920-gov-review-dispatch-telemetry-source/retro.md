**可压缩分析**：主线程 275k 里，**取件复证（≈18 min）是最可压缩的一段**——其中相当比例花在「ARQ 描述与实况不符」的反复核上（三条子项两条半被改写）。但这属于**不可省的核**（见 §3 F2、§5 教训）；真正可省的是**我最初那次路径层级写错导致的无效 census**（§3 F2）。cacheRead 总量 2,822 万是 input 的 ~48 倍——**cache 折扣下真实成本远低于 token 计数呈现的量级**，任何按 raw token 排序的「最贵环节」结论都要先扣这一层。

**首次使用即暴露的实现缺陷（2026-09-21 查明并修正；原诊断错误，见下）**：本批落地后首次采集，`output` 一列对 typed agent（architect 27 条、landing-verifier 58 条）**逐条读成 0**。

> **⚠️ 原归因错误，如实更正。** 我在本 retro 初稿里把它写成「provider 在来源侧不报 `output_tokens`，政策『unknown 绝不写 0』失效于来源侧」，并据此拟了一条 ARQ。**该归因是错的**——真因是**本批自己落地的 `dedupeByMessageId` 取错了去重方向**。

**真因**：transcript 按**流式分块**逐条写（`apiBlockIndex` 递增），而 `usage` 是**渐进更新**的——前面各块 `output_tokens=0` / `stop_reason=null`，**只有末块带完整 usage**。实测（判官 `agent-a80025b139bddfabd`）：

```
id c2e5ce44…  blk=0 out=0   stop=null
              blk=1 out=0   stop=null
              blk=2 out=0   stop=null
              blk=3 out=0   stop=null
              blk=4 out=308 stop=tool_use   ← 真值只在末块
```

而我写的是 **first-wins**（`if (!byId.has(id)) byId.set(id, r)`），于是**每条都取到前面那块 `out=0`，把真值全丢了**。改 **last-wins** 后：判官 `output` 由 **0 → 62,043**、`total` 由 144,986 → **207,029**（**input 两次完全相同**，可见差额纯粹来自 output）。

**为什么自检没拦住**：夹具的 `rec()` 当时生成的各分块 **usage 完全相同**——而那种形态下 first-wins 与 last-wins **等价**，对方向恒真。**这与核验官 2026-09-20 判 RED 的「空壳夹具」是同一个病的第二个面**：那次是去重路径**没被走到**，这次是去重的**方向没被测**。已修：`rec()` 改为忠实复刻流式渐进块，并增两条方向断言；**反向控制实测**——把去重回退成 first-wins，自检由 18/18 变 **11 pass / 7 fail**、exit 1。

**三处连带如实记录**：① 本批 **V9 的证据行**（`tokens.tokenTotals.output = 0`）**就是这个缺陷的现场**，我打印时看见了却解释成了 provider 特性；② retro §2 原表全部作废重算（见上表 footnote）；③ 缺陷**已随本批进入 main**，由 human 2026-09-21 授权走**一次性快速路径**修正（按 AGENTS.md 须诚实记录「跳过流程」——即未走判官评审 + 独立核验的完整 Track B 环，仅以自检 + 反向控制 + 真实数据对账闭环）。

## 3. 摩擦与卡点（按痛感排序）

- **F1 · 验证集的断言被「写成了标签」而非「写成了控制」**（最痛，代价 = 一轮核验 FAIL）：现象 = §5 #1 明文要求主线程侧覆盖「按 `message.id` 去重后累计正确」，我落地的夹具三条记录却全是单块、id 互异 ⇒ **去重路径一次都没被走到**；核验官最小复现 = 把 `readMainThreadUsage` 的 `dedupeByMessageId(principal)` 换成 `principal`，自检**仍 15/15 全绿**。→ 根因 = **我把「夹具里提到了这个场景」当成了「夹具控制了这个场景」**——断言写了 `input === 10`，但那个 10 是在「每条恰好一个块」的输入下算出来的，**换任何实现都能得 10**，故它是恒真式而非控制。→ 证据锚 = `landing-verdict.md` 首轮 §3（含 mutant 命令与 `{"pass":15,"fail":0}` 逐字输出）；处置后 `{"pass":13,"fail":3,"ok":false}` exit 1 含 `main-thread-dedupe-no-inflation`。**与本批主题（静默失真）同族，且是本批唯一的真实缺陷**。

- **F2 · 一次路径层级写错，产出了一个「看起来像结论」的错误数字**：现象 = 我的一次性 census 报「磁盘上 agent transcript 总数 **0**」。→ 根因 = 我把目录层级写成 `<projects>/<slug>/subagents/`，实际是 `<projects>/<slug>/<sessionId>/subagents/`——**少了一层**。→ 证据锚 = 同伴内联脚本首跑输出 `agent transcripts on disk: 0`；修正层级后为 **397**（判官复跑 **398**）。**教训**：**零值/极端值出现在 census 里时，先怀疑测量工具本身**；这一条已写进本批 PROPOSAL 附录「起草期制度教训 3」。(承 §8 旧经验「『已实测』不等于『测对了』」的又一变体。)

- **F3 · 判官自己也产出了一条假 finding，且我差点照折入**：现象 = R1 判 E5「`meta.json` 载体名不实：本机 `meta*` 文件 **0 命中**」。→ 根因 = **判官的搜索 pattern 是前缀 glob `meta*`，而文件 basename 是 `agent-<id>.meta.json`（以 `agent-` 起头）**，永远不匹配——**搜索 pattern 错，不是载体不存在**。→ 证据锚 = 我复跑 `find . -name "meta*"`（无输出）vs `find . -name "*.meta.json" | wc -l` = **398**，且探针文件逐字含 `"model":"haiku"`；R2 判官复跑后**如实自纠**：「根因：文件 basename 是 `agent-<id>.meta.json`…**搜索 pattern 错，非载体不存在**」。**这一条的价值不在「我赢了」，而在：我做了反驳而不是照单折入；判官做了更正而不是坚持。** 若我当时「尊重评审」直接删掉 E5 的载体描述，就会把一个**真实存在且结构化**的字段当作不存在。

- **F4 · 冻结稿与验证集自相矛盾，被验证集自己抓住**：现象 = T2 原文「新增 `payload.mainThreadUsage`」未写明是否无条件带键；而 §5 #4 要求老调用序列产出**逐字段一致**。→ 根因 = **改法段与验证段是分两次写的，我没做一次「两段对读」**——无条件带键会让老形态事件凭空多出一个恒 `unavailable` 段，使 §5 #4 字面不成立。→ 证据锚 = 落地期 V4 首跑发现键集多一项；处置为「仅命中时带键」（取本件既有 `--model` 注释「不传则不带该键」的同一约定），处置后键集与在册历史事件**逐键相同**。**核验官独立判定该处置属「断言校准」而非「未授权改法变更」**（四项理由，`landing-verdict.md` §4）。

- **near-miss（最险一刻）**：**R1 的 S1（未钉死 `tokenUsage.status:'exact'`）若未被打回，本批会「完整落地、全绿验收、目标完全没达成」。** 因为两个既有消费方（`loop-metrics.mjs:242` / `pod-events-aggregate.mjs:76`）**只按 `status` 分桶、不读 `source`**——落一个 `source:'transcript'` 而不置 `status`，新数据会全部落进 `unavailable` 桶，**「tokenExact 覆盖度提升」一点都不会发生，而没有任何门会报红**（本批 §2 T4 自己就写过「这类矛盾不会让任何门变红」）。**没出的原因 = 判官逐字读改法并回到消费方源码核实了分桶键**，而我自己在 §3 消费点表里写的「与 `source` 正交 ⇒ 自动被正确计入」这句**恰恰以 `status:'exact'` 为前提却没说出口**——**我把一个必要前提写成了理所当然**。教训：**「正交」类断言必须把被正交的那个键也钉进改法，否则它就是一句自我安慰**。

## 4. 优化建议（按 ROI 排序）

1. **~~ARQ · `output_tokens` 恒 0 的静默失真~~ —— 本建议已撤回（前提为假，2026-09-21）**：该条原拟按「provider 在来源侧不报 output」立 ARQ。查明真因是**本批自己的 `dedupeByMessageId` 取错去重方向**（first-wins，见 §2 末），**不是 provider 行为**，故**无可固化的外部根因**——已随缺陷一并修正。**撤回本身留痕不删**（防后来者据本行重走一遍）。
2. **ARQ（替换原建议 1）· 夹具输入形态须能让被测差异显现 —— 并附「反转实现必须变红」的反证**：治 F1（核验官 RED）+ §2 末（first-wins 缺陷）——**本批两次缺陷同根**：① 去重**路径**没被走到（夹具记录全是单块）；② 去重**方向**没被测（夹具各分块 usage 等值 ⇒ first/last-wins 等价）。两次都是**夹具输入落在被测差异的盲区里，断言因而恒真**，且**都全绿**过关。候选形态：凡断言涉及「从 N 条中取哪一条 / 按什么键聚合 / 排序或优先级」类逻辑，验证集条目须额外声明**该差异的判别输入**（本批正解 = 造「渐进块」让 first/last-wins 分道扬镳），**判据 = 把实现反转后该断言必须变红**（本批核验官正是这样自证 mutant 的）。载体 = **固化候选 → ARQ 收件箱**（属验证集 / 自检撰写纪律，触 retro 与 acceptance 类 reference；**本批不自立条文**——治理形态变更走既有通道）。预期收益 = 把「恒真夹具」挡在落地前；本批若早有此条，两条缺陷都不会以全绿形态过关。
3. **登记不硬治 · 改法段与验证段须「对读」一遍**（治 F4）：本批 T2 与 §5 #4 的矛盾，本质是**两段分开写、没人做交叉读**。本仓已有「改法文本读两遍（第二遍专抓位置/条件副词）」的纪律（§8 第 7 条），本批证明**还需要第三遍：拿 §5 的每条断言去反问 §2 的改法是否支持它**。载体 = **登记不硬治**：写进剩余计划 §8 可迁移经验（下次起草时人读），不为本条动 G 面。
4. **登记不硬治 · 「ARQ 的处方落点是否还存在」应升为起草期第一问**（治本批取件复证的第三次证伪）：本批子项 b 的处方（「分项入 payload」）**三处早已在位**（旗标面 / `planner.md` 调用行 / 脚本校验），真缺口在上游数据源——**照字面落地会做一堆空改动并声称完成**。§8 已有「先问两问」（是否已被某批消化 / 处方落点是否还在），本批是它的**第三次命中**。载体 = **登记不硬治**（既有经验条已覆盖，本批只添一个实例，不新立条文）。
5. **登记不硬治 · 「零值先怀疑工具」**（治 F2）：已随本批 PROPOSAL 附录制度教训 3 成文。载体 = **登记不硬治**（PROPOSAL 附录已落，不另开条文）。

## 5. 一句总结

成本 **≈39 min 挂钟（含起草→核验 PASS 主环）/ ≈79.5 万 total token（2026-09-21 修正后重算的时点快照；本 retro 初稿写的「58.1 万」系 first-wins 缺陷低报，见 §2 表 footnote）/ 独立面 20.1 min**；触点 **human 2 次**（立项 ack 含三问一次裁完 + 无中途升级）；制品 **4 件齐**（PROPOSAL + landing-summary + landing-verdict + retro）；对照批④（≈126 min / 76.9 万）**约省三分之二**，且**判官两轮即绿、无熔断**。最险一刻 = **S1 未被打回则本批会「完整落地、全绿验收、目标零达成」**（消费方只按 `status` 分桶，缺一个词就整条新源不可归因，且无门报红）。**保险丝判定：两方独立结构（判官独立 + verifier 独立）接住了作者偏差——且是互补不重叠的两次**：判官 R1 抓的是**论证面**（我把必要前提 `status:'exact'` 写成了理所当然），核验官首轮抓的是**实现面**（去重断言被写成恒真式）。两次都出自**同一类我自己的病**：**「提到了」被当成「控制了」**——一处是论证里提到了正交、没钉住被正交的键；一处是夹具里提到了去重、没造出能被区分的数据。**最值得带走的一条**：本仓的「两方独立」不是冗余——本批若不派核验官，一个**全绿但空壳**的验证集会随 FROZEN 进入长期资产，此后每批都会照着它抄。
