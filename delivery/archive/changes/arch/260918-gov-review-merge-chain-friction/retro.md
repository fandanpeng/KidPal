## 3. 摩擦与卡点（按痛感排序）

**F1 · ARQ 的「建议改动」是待验证假设，不是执行指令（本族最痛、本批首次撞出）**
- **现象**：`ARQ-260909-gate-green-anchor-regex-loose` 的处方写「regex 收窄至『verdict/结论 同段』形态与注释意图对齐」。照做写进 T1 后，R1 判 BLOCKING（F1）：实测**真实判官 verdict 形态 ≥8 种、跨两套惯例**（§7 内联 append / 独立 `review-*.md` 文件），**该描述不成立**——`**GREEN（可 FROZEN）**`（行首加粗独立形态，跨 4 批）与 Status 行轮次指针 `R2 GREEN〔…〕` 都**不含 `verdict/结论` 标签**。
- **根因**：ARQ 是「执行测出问题」时登记的——登记做到「**看清现象**」，**没做到「验证改法」**；而「建议改动（候选，交 review，不自批）」的措辞容易被读成「已收敛的执行指令」。
- **证据锚**：§7 R1-F1 原文（含逐份 26 份 arch PROPOSAL 的 regex 对照实测）；队列行 `ARQ-260909-gate-green-anchor-regex-loose` 的 **2026-09-19 追记**。

**F2 · 「恒真」的真机制与 ARQ 原归因不同（起草期自查挖出）**
- **现象**：我在 §1 原把「恒真」归因于「判官 verdict 行命中裸分支」。起草期自查实测推翻：真机制是 **`PROPOSAL.template.md` 头部样板行「**结构字段硬条款**：…：**GREEN 结论前必须在场**」自带 GREEN**——存在于 **16 / 26** 份 arch PROPOSAL，**它单独一个就让现行 regex 为真**，与判官判没判无关。
- **根因**：模板样板是**每份 PROPOSAL 都会复制**的结构字段，而它的措辞里含关键词——做「全文 token 匹配」类判据时，**模板自身的词汇会污染判据**。
- **证据锚**：§6 留根① 的「真机制更正」段；队列追记同载。

**F3 · 四个候选设计全部实测不成立（起草期普查）**
- **现象**：对全部 26 份 arch PROPOSAL 逐份实测四个候选：行首/引导形（**漏 3 个已冻结批** = 会错拦合法合并）、行内宽松（太松，草案即判真）、判定陈述位置（同样漏 3 个已冻结批 + 误判治理类草案）、只排样板行（0 假阴性但仍有 5–6 份非 GREEN 文本判真——**含治理类正文自己讨论 GREEN 时，即最相关的那一类**）。
- **根因**：**「错拦合法合并」与「闸继续虚设」之间没有免费的中间点**——这是判据设计问题、非一行 regex 可解。
- **证据锚**：§6 留根① 的四候选实测表。

**F4 · 撤跟踪的跨工作树过渡（已预判、已申报，未造成事故）**
- **现象**：11 件 `overlap-probe.json` 撤出索引后，ff 合并进 main 时它们会从 main 工作树盘上消失；Pod 工作树若带本地脏 probe 会撞一次。R1-F5 事先点出，落地 summary §3-2 如实申报。
- **根因**：索引态变更的过渡代价**不可消除、只能申报**（文件可再生、无数据丢失）。
- **证据锚**：§7 R1-F5；landing-summary §3-2。

1. **ARQ「建议改动」应显式标注验证状态**（载体：**ARQ 收件箱 / `/loop-retro`**）——本批 F1 的处方若在登记时就带一句「**改法未实测，起草时先复证**」，能省一整轮 BLOCK。**最轻做法**：在 `gov-arq` skill 与队列 §0 维护规则里，给「建议改动」段加一句常设提醒。**本批三批（P1/P2/P3）各撞一次同类，ROI 最高。**
