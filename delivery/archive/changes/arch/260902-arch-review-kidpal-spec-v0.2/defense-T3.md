# Defense — T3 提醒投递状态机（defender 答辩）

> defender 轮产出（2026-09-02）。主线程代落盘，内容保真。对 `findings-T3.md` 逐条答辩。

**T3-F1 · CONCEDE（边界精确化）**｜轴 6 打的两处 handoff，charter 自己已在 §4.3 留空点承认——D-5/E-2「谁检测 schedule.md 变更并触发推送，spec 未名之」（charter:99/:114-115）。但须纠正 challenger 的「owner 全缺」口径：`(1a)` owner 与概略触发其实有字——spec:325「OpenClaw cron…按 schedule.md 算好三档时刻、把每档提醒条目写入 alerts/pending.json」+ charter E-1「OpenClaw cron（三档阶梯排程）定时扫 schedule.md」= cron 定时扫即重算触发；真正缺失的是「**新建日程后的即时重算三档**」（spec:588 决策 26 的「即时推」只覆盖 P1「接下来」刷新，不覆盖提醒三档）与「cron 扫频/节奏」。`(1b)` 「到点检测 owner」同样有字——spec:325「网关只做到点经 WS 推送」+ 决策 18「提醒定时推送（各约几十行）」（spec:580）即网关侧 push helper；真正缺的是「pending.json 从 OpenClaw 进程到流式网关进程的传递机制（同机共享目录轮询 / cron loopback 调 helper / 队列）」，spec:567 决策 5 只证「同机」未证「机制」。S6 关联成立：预排 vs 惰性重算未定 → 离线一周重连的「过期静默作废」评估时点不可判。**改法方向**：在 S-F1.4/决策 20 补一句「cron 扫频 + pending.json 传递通道（同机）+ 三档重算粒度」；不引入人工门（纯实现机制澄清，契约门 §四 push helper 定义可顺带收口）。

**T3-F2 · CONCEDE（BLOCKING，真实矛盾）**｜spec:326「重推的同 id 直接回回执不再排队（幂等，重复弹窗根除）」vs spec:327「队列中未渲染的条目待渲染后才回回执」确实两不可调和。challenger 论证成立：若幂等集合「渲染完成才入」→ 队列中未渲染条目 60s 重推窗口内不在集合 → 重推再入队 → 重复弹窗（违背 spec:326「根除」）；若「接收即入集」→ 与 327「待渲染才回执」撞（接收即回执 = 把「渲染即确认」变成「接收即确认」）。触发正是 S4(a)+(c)（charter:65-68）07:45 N 条目共享墙钟 + 驻留到按键 + 60s 重推 → 第 2…N 条待渲染期被重推是叠加态非边角。「重推只命中已渲染态」的消解不成立——网关重推的是「未收渲染回执」的条目，而未渲染的排队条目恰恰未回执。矛盾根源：spec:326「同 id 直接回回执」是一句覆盖「已渲染（回执丢失被重推）」与「已接收未渲染（正在排队）」两态的过度压缩表述。**改法方向（守住 P4「渲染即确认」已裁取舍，不改「接收即确认」）**：解耦两件事——(a) **幂等去重 = 接收即入集**：设备**接收到**提醒条目（入队前）即把 id 记入易失 known-id 集合，作用仅「屏蔽重复入队」，与渲染无关；(b) **回执出队 = 渲染即发**：回执仍只在弹窗渲染完成时发（不动 P4）。于是「同 id 重推」两态分别处置：已渲染 → 补回回执（根除重弹）；未渲染（排队中）→ 去重不重复入队、**不回执**，等渲染后回。spec:326 该句需改写为这一两态版；可选规范化为 received/queued/rendered/acked 四态、把「设备侧止弹（rendered）」与「网关侧出队（acked）」显式分开。此方向不引入人工门（轴 11 红线守住），但「幂等集合是否含已接收未渲染」本身是一次产品语义裁定点，需 human 拍板（challenger elicitation「核心」成立）。

**T3-F3 · CONCEDE**｜spec:326「重推的同 id」预设 id 跨重推稳定，但 id 的生成 owner 与稳定性在 spec 全无字——spec:325 只列「含 fire_at + 文案」未提 id；契约变更包 :31 只是 `"id": "<reminder-instance-id>"` 占位未定义。轴 9「声明的不变量可强制」确实不满足：幂等去重依赖的键自身无定义。cron 每次重算覆盖写 pending.json 是否重新生成 id（若按时间戳重生成 → 旧 id ≠ 新 id → 按新 id 重排队 → 重复弹窗）无保证。**改法方向**：决策 20/S-F1.4 补一句「幂等 id = reminder instance 稳定标识，OpenClaw cron 首次生成后跨重推/重算不变（确定性散列自 schedule 条目 + 档位 + 事件日期）；cron 重算复用既有 id 不重生成」。该字段级事实同为契约门 §三（CDQ-260902）需锁定项，与 T2 联动。

**T3-F4 · CONCEDE（边界纠正）**｜challenger 的「带物唯一承载面蒸发、无回读路径」过强——带物持久 source 其实是 schedule.md 备注列（spec:319「携带内容…走课表备注列承载」），并非真蒸发；S-F1.3 语音问课表（spec:308-314）**潜在**可读回该列。但真实缺口成立：spec:294（P1 分组不含备注）与 spec:303（P2 每行仅圆点+时间+课程名+地点）确无备注回显；spec:313（S-F1.3 验收）未明确备注列参与答复。于是孩子错过 20:30 档（渲染即出队、不重推，spec:326）后，「带物」在常显 UI 面无补偿可见，与 spec:317「不丢三落四」目标之间存在张力，且 spec 无缓解声明。这与 challenger 的定位一致：不打「渲染即确认」取舍，打「信息承载面无持久 UI 回显」的实现含义。**改法方向**：S-F1.4 或 S-F1.3 补一句「带物/备注除 20:30 提醒外可经语音问课表读回（S-F1.3 明确备注列参与答复）」；可选 P1『接下来』带物项附星标（复用 S-F1.2 既有星标呼应 spec:306）。不引入人工门（challenger 已自判，轴 11 无违规；附议）。

**T3-F5 · CONCEDE（部分，严重度微调）**｜`(1)` 「不设上限——提醒低频」（spec:327）确为 assertion 非不变量，但 challenger 的「无界」过强——队列深度在领域上**天然有界** = 当天有效事项数（家长录入课表条目，个位数至十几条，spec:327 前提即「提醒低频」），非真无限；真实缺口是 spec 未量化此界、未声明极端堆积（孩子整晚不按键）的行为，属 SHOULD 下缘（近 NIT）。`(2)` 才是实缺口：spec:326「过期静默作废」明文只覆盖「未送达」；**已渲染但永未按键**的弹窗「驻留到按键」（spec:327）永不过期，可滞留屏上越过事件本身，spec 无设计响应——且此滞留弹窗会阻塞队列后续提醒（spec:327「不合并、不替换」），导致后续条目「被饿死在队列 → 未渲染 → 60s 重推 → 3 次后作废」，与 F2 联动放大。**改法方向**：不改「驻留到按键」取舍（不自动强迫关闭），补「已渲染弹窗在 event 时刻过后允许后续提醒顶替/降级显示（早已出队，非追加送达）」或「event 过后弹窗降为非阻塞提示」；并声明队列积压的极端行为。不引入人工门。

**T3-F6 · CONCEDE**｜charter S3 明文要求「检查『提醒 TTS 合成随推送实时发生』是否使提醒链路对 TTS 可用性有隐性同步依赖」（charter:60-63）。spec:328「网关合成 TTS 随推送一并下发音频」+ spec:589 决策 27 均未给降级响应；spec:266「云端任一环节失败 → 固定安抚句」是语音会话兜底，非提醒推送兜底；决策 18/2「可替换 provider」（spec:580/A2 spec:102）是运维级换供应商，不解「推送当口 TTS 挂掉的瞬态降级」。**改法方向**：声明提醒弹窗与 `speech` TTS 解耦——「弹窗+提示音」必达（不依赖 TTS），`speech` 为可选增强，合成失败/超时则本条目降级「仅弹窗+提示音、静默不附 speech」（或 speech 异步补发、不阻塞弹窗）。纯技术降级声明，不引入人工门。

**T3-F7 · CONCEDE**｜spec:111 单行三处确与冻结决策冲突且核实属实——「事前 30 分钟」vs spec:582「事前 15 分钟（human 修订值）」；「确认即清」vs spec:326「渲染即确认、即出队」；「推送 `alert` 消息」vs spec:585「统一走 mcp kidpal/alert」+ spec:538「小智原生 alert/custom 通道弃用」。属文本同步。**清理口径**：spec:111 三处值分别对齐 spec:582（15 分钟）/spec:326（渲染即确认出队）/spec:585+538（mcp kidpal/alert）；(3) 及 spec:80「提醒走 alert 消息」、spec:134（E3 与决策 23 冲突）为通道命名漂移，转 T2 统一收口，本支仅确认其与冻结决策的冲突事实。

**T3-F8 · CONCEDE（NIT）**｜spec:325「网关只做到点经 WS 推送 + **标记送达**」的「送达」与 spec:326/538「送达确认 = 渲染回执」（spec:538「设备 JSON-RPC 回执 = 送达确认」）同词异义——325 读作 push 时刻标达（即 charter §7 P4 注「被第二轮推翻的『推送成功即送达』」，charter:171），326/538 读作回执才达。builder 歧义属实。**改法方向**：spec:325 改「标记已推送（重试计数用）」，与 challenger 建议一致；不动 326/538 的「回执出队」语义。

## 摘要

- **verdict 计数**：REBUT 0 · CONCEDE 8（其中 F1/F4/F5 为「CONCEDE + 边界精确化」——分别纠正 challenger 的「handoff owner 全缺」「带物蒸发」「队列无界」三处过强表述，但不改变 CONCEDE 结论）。
- **BLOCKING 1 条**：T3-F2，去重回执矛盾真实成立；修法方向 = 解耦「幂等去重（接收即入集）」与「回执出队（渲染即发）」，守住 P4「渲染即确认」不改「接收即确认」，可规范化为 received/queued/rendered/acked 四态。
- **需 human 拍板**（非 deadlock）：T3-F2 的修法本身含一次产品语义裁定——「幂等集合是否含已接收未渲染的队列成员」。challenger 与 defender 在「矛盾真实」无分歧，分歧只在「解耦口径」，方向明确、不僵住，但需 human 确认新版口径。
- **deadlock 候选**：无（无「既无法 REBUT 又不愿 CONCEDE」项）。
- **轴 11 立场**：全程无违规。所有 CONCEDE 改法（F1 机制澄清 / F2 状态机解耦 / F5 过期降级 / F6 TTS 降级 / F4 回读路径）均保持纯自动、未引入「家长逐条确认」第七人工门；challenger 也已自判「轴 11 无违规」+「T3-F2/F4 落点是轴 9 不变量完整性」，附议、并据此把 F2/F4 的修法钉在「去重口径 + 补偿可见性」上而非「加人工审批」。
- 已接受前提（human 已裁）未被攻击：渲染即确认、不重推、驻留无超时、不设上限、排队，全部按 charter §7 只攻其一致性/完整性/实现含义。
