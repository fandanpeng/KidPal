升档规则与跳过例外 比例化的两处接缝

升档规则

档 1 起草期发现牵连面（关联 story / §2 共享底座 / 线框需同步）即携带清单；牵连 ≥2 处或含 NFR / Epic → 升档 2。升档裁定 = 主线程提呈、human 确认。

跳过例外（一次性）

档 1 级语义修改，human 明确说跳过流程的一次性操作允许直改（对齐 AGENTS.md Hard Rules 既有条款）；§9 记账须写明「跳过 story-author / reviewer」。例外不能顺手扩大成常态。

定稿载体与下游消费 冻结的不是文件，是「版本行即 changeId」

定稿载体

  • story 修订定稿的标记 = §9 版本行本身，版本号即 changeId（不另铸批次 ID——TaskPackage changeId 强语义，撞名禁用）
  • 实现包引用 story = S-Fx.y · 标题（+ 可选 AC 号集），之上可加「定稿版本号」
  • 实现包 launch 前置：带 spine 的变更，facePlan 中先于实现面的各面 anchors 未回填 = 上游未冻结 → 不得 launch

REQ- 域 CRQ 闭环纪律（docs/crq/requirement/）

  • owner：指向需求变更流程某档或 human——禁空
  • trigger：何种事件触发捡起——须可判，禁「human 想起」形态
  • 销行条件：通常 = 对应需求变更 §9 定稿；销行跑 node .claude/scripts/crq-render.mjs 自动归档
红线：reviewer 四查 = ① 意图保真（对着 human 原话逐条核）② 纪律合规（write-story 完稿自检全项 + 锚机检绿）③ 撞车复核（独立重扫，不信 author 的报告）④ 牵连面完整；不代笔，改稿回 author。story-author 与 requirement-reviewer 不得互兼。触 docs/contracts/** 的发现一律路由 architect-reviewer 四分类 + 人类契约门，本流程无权处置。
