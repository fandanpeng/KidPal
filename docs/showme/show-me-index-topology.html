CodebaseMemory 索引拓扑：主仓 ⇄ Pod worktree

事实核实于 2026-09-23（本机实测：list_projects 31 项、git ls-files -v skip-worktree 标记、~/.cache 逐项目 DB、两份 artifact.json 对照）

一、三层结构（谁存什么）

① 工具缓存（真正的图）

~/.cache/codebase-memory-mcp/<项目名>.db —— 每个项目一个 SQLite，互不相干
  • 主仓：C-AI-KidPal.db 41.6 MB · 17952 nodes
  • 本 Pod：C-AI-KidPal-pod-m1-k1a-….db 54.8 MB · 17952 nodes
  • 另有 5 个参考工程 + KidPal-claude，共 31 个项目
图查询（search_graph / trace_path）读的就是这一层。

② 仓内快照（可分发的那一份）

<worktree>/.codebase-memory/ —— 随 git 走的压缩快照
  • graph.db.zst（zstd；主 8.39 MB / 本 Pod 7.16 MB）
  • artifact.json（元数据：commit / indexed_at / project / nodes / edges / 大小）
  • .gitattributes：graph.db.zst binary merge=ours —— 合并冲突天然免

三、三条关键规则（容易踩的点）

命名 = 路径派生

C:/AI/KidPal → C-AI-KidPal；C:/AI/KidPal-pod-x → C-AI-KidPal-pod-x。
刷主仓不要传 name——手动另传名会在同 root 造出第二个条目（曾实测发生）。

索引跑哪个 path，就刷哪个 path 的快照

在 A worktree 里对 B path 建索引，会改写 B 的 .codebase-memory/。跨目录实验要小心（本会话就误改过一次，已复原）。

mode 只在「从零建」生效

已有索引再跑 index_repository(mode=…) 是空转（实测 node 数逐值不变）。
实测差：full 17952 nodes vs moderate 10142——moderate 砍的主要是 Variable 节点（3194→1226，−62%），Function/File 只降 ~9%。

Pod 快照为什么是本机私有

Pod worktree 的 artifact.json / graph.db.zst 标了 skip-worktree（git ls-files -v 显示 S）——索引器持续自刷新、不进 Pod 的提交；只有主 worktree 那份才上 main 分发。
一句话总结：图本体住在工具缓存（每项目一个 DB，互不相干）；可分发的那一份是各 worktree 里 .codebase-memory/ 的压缩快照；同步方向是单向的——主 worktree 偶发把快照 commit 上 main，再经 merge 分发到 gov / Pod，Pod 启动时用它做「导入 + 增量补差」建自己的索引。
