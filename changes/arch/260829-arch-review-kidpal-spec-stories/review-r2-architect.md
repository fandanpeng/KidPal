### B1 · KEY 长按定义冲突 —— **部分修复（spec 侧已修复，设计稿侧未收口）→ 仍打回**

human 裁定：KEY 长按 = 回首页（不是 P4 查下一个字）；P4 查下一个字改走语音。

spec 侧（已修复，四处统一为「回首页」）：

- §4.0 注：`「查下一个字」不占键——P4 想查新字直接语音说（如"那『星』字呢"），走 S-F3.1 查字链路；KEY 长按专职回首页（2026-08-29 human 裁定 B1）`（spec.md:281）✓

设计稿侧（**未收口，仍作旧语义**）：
- gesture-table：`<span class="kd">KEY</span> 长按 | 预留，暂不定义 | P4 查下一个字的候选触发`（kidpal-ui-design-v2.html:620）——与 spec「回首页」直接矛盾。
- P4 画布底部提示条：`下一个 <span class="kd">KEY</span><span class="kcap-note">长按</span>`（kidpal-ui-design-v2.html:1002）——仍把「查下一个字」绑在 KEY 长按上。

问题：B1 是 R1 唯一 BLOCKER，核心是「同一颗键的长按到底干什么」须定一尊。spec 侧已定（回首页），但 human 裁定 m5 时确立的原则是「设计稿是真相源，砍/改功能须在设计稿侧同步标注或修改」。B1 改了 KEY 长按的既有语义，设计稿 :620 与 :1002 是该语义的承载处，却原样保留旧定义。实现方读设计稿 gesture-table 会得出「KEY 长按=P4 查下一个字候选」，与 spec 冲突——正是 R1 B1 想消除的二义性，只是从「spec 内部 §4.0 vs §5.3」转移成了「spec vs 设计稿」。

建议改法（不升 human，human 已定 B1 方向，此处只是把它落到设计稿侧）：将设计稿 :620 改为 `KEY 长按 | 回首页 | 所有页面一致`（与 spec §4.0 一致），并将 P4 底部 :1002 的「下一个 KEY 长按」改为语音引导（如「说『那星字呢』查下一个」）或加注「已改为语音，见 spec S-F3.3」。这是 m5 确立的「设计稿同步收口」动作在 B1 上的同款执行。
