现在 vs 将来one idea, stated once

现在（ARQ 实测的洞）

  • input = 「plan 或想法」，形态随 human 手头的东西走
  • 意图无耐久载体——只以「投影进实现 plan」的方式幸存
  • 跨面 idea：human 在 3-4 个窗口、3-4 种留痕格式重复同一意图
  • 触面靠事后逃生门踢走；② 单包路径跨面顺序无机制保障
  • 窗口间接力靠 human 手工：起新会话、想启动 prompt、重新陈述

将来（本稿）

  • input = human 原话（一次） + agent 四面探测结果（两层）
  • intent 物化为 spine：delivery/changes/intake/<changeId>.md
  • 四面门照旧各归各裁——统一 intake ≠ 统一门
  • 各面产物逐面回填 spine anchors——跨面顺序可机查
  • 接力 = 主线程 headless 拉起下游编排会话；门停机 + --resume 接住

发起机制主线程怎么把各面流程跑起来

姿势一 · 同会话内联（轻面）

主线程自己就是编排者，直接一级派发子 agent。 适用：需求档 0/1、单步小活——requirement-change 档 1 本来就是主线程 dispatch 设计（story-author 同会话 return + reviewer dispatch prompt），不需要新机制。

姿势二 · headless 接力（重面）

主线程经 Bash run_in_background 拉起 claude -p——它是完整顶层会话，不是子 agent，可 --agent 跑完整编排循环（对抗 review / 多 Pod 拆包）。 适用：架构 Track A/B、契约 packet 起草、③ 拆包。长循环超 Bash timeout，必须后台 + 通知回调；子会话 stdout 只是进度，状态一律以 spine 落盘为准。
# intake 主线程按 facePlan 顺序逐面推进（runbook 在 intake 时定死） claude -p "读 delivery/changes/intake/<changeId>.md， 只执行 facePlan 的 arch 面；开场先查上游 anchors 是否已回填； 完成后回填自己的 anchor；遇 human 门 → status 写 awaiting-human 后退出报告； 执行中有疑问 → 写 spine openQ 退出，等待主线程答复" \ --agent review-moderator --settings <面专属 settings> # 门停机后 human 接住：同一会话、上下文无损 claude --resume <session-id> # human 进门拍板，拍完续跑 # 疑问答复：主线程能答的写回 spine openQ → 再次 headless 续跑；不能答的呈 human
headless 是省「agent 之间的接力」，不是省「人的判断」——命令行显式钉 --agent + 面专属 settings（ARQ-260918 贴卡起步丢身份的坑）；子会话禁止再 claude -p 拉孙会话；这两条第一版靠 prompt 纪律，机检齿留 G3。

门的弹出时刻哪些门、何时弹、弹给谁

门本身一个不加一个不减（统一 intake ≠ 统一门）——下表只把既有门按「headless 流里怎么表现」重新摆一遍：
门所在面何时弹出（触发条件）headless 流里的行为类别
立项 ackintake intake 收尾，四面对齐「为什么改 / 往哪改 / 改动多大」——intake 会话内 AskUserQuestion 交互式会话内，天然在场，不涉 headless 恒停
升级判据intake 探测命中：触 docs/contracts/** / 跨系统结构性变更 / 存疑向严 → 不入 Track B，转 Track A intake 会话内路由裁定，随立项 ack 一并呈 恒停
human 契约门契约面 architect-reviewer 四分类判「确需改」或「spec↔contract 漂移」 必停：status 写 awaiting-human，human --resume 签字 恒停
FROZEN 盖章实现面③ 仅大 feature：workstream PROPOSAL 落盘后（作者≠判官——architect 起草，human 盖；portfolio-planner 只拆 FROZEN 件）。不是盖 spine——spine 是路由账本，免冻，只记各面自己的冻结态；facePlan 修订权：加面/改「谁裁」= L2 呈人，调顺序细节 = L0/L1。Track B 治理批另有第 3 步 FROZEN，由主线程凭「立项 ack + GREEN」机械地标，非 human 触点 必停：awaiting-human，human 盖章后续跑 恒停
熔断三选一架构面 对抗 review 3 轮未 GREEN（转 Track A / 撤回缩圈 / 换判官再战 1 轮） 必停：三选一是 human 决策，resume 后按选择续 恒停
需求终拍需求面 仅档 2（结构性：story 新增/重写/砍除、跨 story 连锁、NFR/Epic）——architect 可行性 + reviewer 结论一并呈 档 2 才 headless 起面 → 到此必停；档 1 无终确认（§9 append-only 事后否回），可全程 headless 内联 按档
升档确认需求面 档 1 起草中发现牵连 ≥2 处或含 NFR/Epic → 升档 2（主线程提呈、human 确认） 子会话停 → openQ 写疑问 → 主线程呈 human；答后 resume 续跑 按档
例外升级架构面 Track B 例外清单命中 / 评审打回项影响目标效果 / 判据适用存疑（存疑向严） 命中才弹：停 + 呈 human；不命中全程 headless 跑完 条件弹
触点① 路由确认实现面 architect 四档裁决后、落盘前（Lite/Full 安全相关） 有既有预授权通道：六条件全满足可免问；命中「必须回问枚举」（升档 / security 轴 / 方案变形 / 新情形）则停 条件弹
supervisor 升级实现面 riskTier=high；或 verifier↔fixer 轮次超预算 停 + 呈 human（既有 dev-loop 行为不变） 条件弹
launchPreconditions实现面 launch 上游面（story/arch/contract）anchor 未回填 = 未冻结（建议 3 推广到 ② 路径） 不弹人：机查自动等待——不是问题，是顺序；上游回填后自动可 launch 机查
（免门对照）需求档 1 终确认需求面 无门——§9 append-only 事后否回兜底（260928-gov-review-requirement-face 已裁） 档 1 全程无需人出场 免门
升级判据 ≠ 契约门（两道题，不是一件事谈两遍）：升级判据是路由——触面是「疑似触碰」，此时没有任何契约 diff 存在，human 拍的是「走哪套流程」，判错代价 = 白走一段流程（可挽回）；契约门是审批——针对一份具体的 ContractChangePacket 文本，human 拍的是「签不签」，判错代价 = 污染单一事实源（不可挽回）。两道门独立可达：触 ≠ 改（升级后四分类可判「无需改」，契约门不出场）；没升级也会撞门（逃生门 reviewer-first 从任意面把契约改动踢进契约门）。
接缝去重：intake faceMap 的契约行（动不动 / 动哪 / 依据行号）直接作为 architect-reviewer 四分类的输入——契约门开场带 intake 取证，human 第二次出场只答「签不签」，不重听诊断。

疑问三级处置子流程有疑问：主线程能解决的就地解决，不能解决的再问人

L0 · 子流程就地解决 疑问属于执行歧义且 canonical 文本有依据可引（references / 既有先例 / story 原文）——不涉门语义、不越权限、不创先例、影响限于本变更内 → 子会话直接按依据办，裁定 + 依据写进 spine openQ 留痕，不打断流程。
▼ 答不了无依据可引 / 触门·档位·权限语义 / 存疑
L1 · 主线程答疑 子会话把疑问写 spine openQ + 退出报告 → 主线程先接：能答的（分面计划内已有裁定、跨面上下文主线程有而子会话没有的）写回 openQ → headless 续跑，human 不出场。主线程答的也留痕。
▼ 主线程也答不了判据存疑（存疑向严）/ 枚举外新情形 / 需要取舍
L2 · 呈 human 主线程不猜、不代拍——随下次必停门一并呈，或单独 awaiting-human 停机。对齐既有纪律：触点①预授权「枚举外新情形一律回问」+ Track B「存疑向严」——这两条从触点①推广到全部子流程疑问。
为什么主线程适合当 L1：跨面上下文（faceMap / facePlan / 立项 ack 时 human 的取舍倾向）只在 intake 主线程会话里完整存在——子会话答不了的很多问题，主线程凭 spine 就能答，不该消耗 human 的出场。

比例化：什么时候才建 spine机制只落在需要的地方

单面 ① 直接修免门（地板不变）——无 spine。
单面 ②③现状不动：plan.md / PROPOSAL 本身已载 intent，无重复陈述问题——无 spine。
触面 ≥ 2spine 强制。唯一新增前置物；重量 ≈ 30-60 行 frontmatter + 分面计划，v1.56 那种口头需求 + 小修也能扛。
已拍（2026-09-28 讨论）：① spine id = 全局 changeId，各面锚回填映射既有格式，单包 ② 复用不另铸；② intake 不进 changes-index 的 lane INDEX；③ 发起 = 轻面内联 + 重面 headless 接力，gate 停机 + --resume 接住（human 提议）；④ 疑问三级处置 L0 就地解决 / L1 主线程答疑 / L2 呈人（human 原则，判据细化留 PROPOSAL）。
留 PROPOSAL：四面探测的深度与派发形态；grilling 收敛的具体接线；/arch-change 退役安置；headless 禁跨门·禁递归·身份显式三铁律的成文位置与机检齿（G3）；L0「有依据可引」的判定口径。
